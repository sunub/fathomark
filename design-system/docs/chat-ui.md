# Fathomark Chat — UI 사양

Obsidian 오른쪽 패널에 사는 사이드바 에이전트. 이 문서는 디자인 캔버스를 글로 옮긴
것입니다. 캔버스가 그림이고 이 문서가 계약입니다. 둘이 어긋나면 조용히 한쪽을 고르지 말고
둘 중 하나를 고치세요.

기준 폭은 **400px** — Obsidian 오른쪽 사이드바의 실사용 폭입니다. 레이아웃은 대략
320–520px에서 버텨야 하고, 아래의 어떤 것도 정확한 폭에 의존하지 않습니다.

토큰은 [`src/styles/fathomark.css`](../src/styles/fathomark.css)에 있습니다. 모든 색은
LLaMA CLI 테마(`obsidian-mcp-server/src/cli/theme/`)에서 왔고, 그래서 플러그인과
터미널이 하나의 제품으로 읽힙니다.

---

## 1. 크롬 규칙

실수로 가장 자주 깨지는 규칙이라 맨 앞에 둡니다.

- **패널 안에 구분선을 두지 않습니다.** 헤더 아래 `border-bottom`도, 컴포저 위
  `border-top`도, 섹션 제목 옆 헤어라인도 없습니다. 400px 패널을 가로선으로 잘라 띠로
  만들면 실제보다 좁아 보입니다. 섹션은 여백으로 나눕니다.
- **테두리는 "이건 당신이 조작하는 것"이라는 뜻입니다.** 카드, 칩, 컴포저가 테두리를
  갖습니다. 레이아웃 컨테이너는 절대 갖지 않습니다.
- **패널 안에 제품명이나 마크를 넣지 않습니다.** Obsidian이 이미 자기 탭에서 이 뷰의
  이름을 말합니다. Fathomark 마크는 정확히 한 번, 빈 상태에만 나타납니다.
- **단일 요소 위에 대문자 라벨을 두지 않습니다.** 컨트롤을 이해시키려고 라벨이 필요해
  보인다면, 먼저 그 컨트롤이 이미 같은 말을 하고 있지 않은지 확인하세요. 섹션 제목은
  11.5px / 600의 문장형입니다.
- **대문자는 상태 배지 전용입니다** — `STREAMING`, `COMPLETE`, `FAILED`,
  `NOT APPLIED`, `LOCAL`. 이것들은 라벨이 아니라 데이터입니다.
- **아이콘만 있는 버튼은 `aria-label`을 갖습니다.** 상호작용하는 모든 것은 진짜
  `<button>`, `<a href>`, `<input>` + `<label>`이고, 클릭 핸들러를 단 `div`가 아닙니다.

## 2. 색은 의미를 나릅니다

이 UI에서 색은 둘 중 하나를 답합니다. *이건 어디서 왔는가?* 또는
*지금 런이 무엇을 하고 있는가?* 장식으로 칠하는 색은 없습니다.

| 토큰 | 의미 | 나타나는 자리 |
|---|---|---|
| `--fm-brand` | 에이전트 자신 | 전송, 적용, 스트리밍 캐럿, 메모리 아이콘 |
| `--fm-vault` | 사용자 자신의 노트에서 온 증거 | vault 툴 행, 노트 칩, 인용, wikilink |
| `--fm-external` | 네트워크로 가져온 증거 | Wikipedia 툴 행과 인용 |
| `--fm-pending` | 미검증, 또는 사용자를 기다리는 중 | 근거 없는 주장, 출처 충돌, 예산 압박, `NOT APPLIED` |
| `--fm-error` | 런이 실패함 | 실패 카드, Stop, 연결되지 않는 모델 |
| `--fm-ok` | 모델에 닿음 | 모델 상태 줄의 점, 그 외에는 없음 |

말해둘 만한 결과가 둘 있습니다.

- 브랜드 보라는 증거 위에 절대 얹히지 않습니다. 인용이 보라색으로 보인다면 잘못된 건
  색이 아니라 그 인용입니다.
- 네트워크 읽기는 전부 눈에 띄게 파랗습니다. 사용자는 한 글자도 읽지 않고 이 런이 기기
  밖으로 나갔는지 알 수 있습니다.

`--fm-brand` 채움 위의 글자는 흰색이 아니라 `--fm-brand-ink`(거의 검정)입니다.
`#9b7ff6` 위의 흰색은 약 2.8:1로 통과하지 못합니다. `--fm-pending`과 `--fm-error`
채움도 마찬가지입니다.

## 3. 두 개의 목소리

| 목소리 | 서체 | 쓰는 곳 |
|---|---|---|
| 산문 | `--fm-font-sans` (Public Sans), 13px / 1.62 | 모델이 말하는 모든 것, 사람이 읽는 모든 라벨 |
| 기계 | `--fm-font-mono` (IBM Plex Mono), 11.5px | 툴 이름, 토큰 수, 파일 경로, 줄 범위, 런 id, 소요 시간 |

CLI와 같은 관습이고, 독자가 모델의 주장과 하네스의 측정값을 구분하는 가장 빠른
방법입니다.

## 4. 셸 구조

모든 **주** 화면은 같은 세 부분을 같은 순서로 갖습니다.

```
┌──────────────────────────────────┐
│ 헤더              44px, 선 없음   │  메모리 · [상태 배지] · [런 메타]   ⟶ 히스토리 · 설정
├──────────────────────────────────┤
│                                  │
│ 본문            flex-grow        │  빈 상태, 또는 대화
│                                  │
├──────────────────────────────────┤
│ 하단                              │  상태별 행 → 예산 바 → 컴포저 → 모델 상태 줄
└──────────────────────────────────┘
```

### 헤더

44px 고정. 왼쪽은 메모리 아이콘, 런이 있으면 런 상태 배지, 그다음 런의 모노 메타데이터.
오른쪽은 히스토리와 설정 — 언제나 둘 다, 언제나 그 순서로. 그 외의 것은 들어가지
않습니다.

### 하단

주 화면에서는 하나의 컴포넌트이고, 순서는 이렇습니다.

1. **상태별 행** — 런이 끝났으면 답변 액션, 아이들이면 없음
2. **예산 바** — 항상, 언제나 여기, 다른 어디에도 두지 않음
3. **컴포저** — 항상 존재하고, 제거되지 않음
4. **모델 상태 줄** — 점, `모델 · 엔드포인트`, `LOCAL`

컴포저가 예전에 깨지던 규칙입니다. **사라지지 않습니다.** 스트리밍 중에는 Stop이 전송
버튼 자리를 대신할 뿐이고, 입력 필드는 그대로 쓸 수 있으며 거기 친 내용은 현재 런 다음에
실행됩니다. 실패는 런의 상태이지 패널의 상태가 아닙니다.

### 예산

같은 숫자는 언제나 같은 모양으로 그려집니다. 모노 `used / total`, 무엇이 채우고 있는지에
따라 색이 나뉜 막대(브랜드 = 지시문과 메모리, vault = 노트와 증거, external = 가져온
페이지, 회색 = 출력 리저브), 그리고 오른쪽의 리저브 라벨. 컴포저 바로 위에 두어서
"예산을 넘겼다"와 "그럼 무엇을 뺄까"가 한 시선 안에 들어오게 합니다.

## 5. 런 상태

```
idle → preparing context → waiting for model → streaming → executing tool
     → awaiting approval → complete | cancelled | failed
```

헤더 배지, 컴포저, 모델 상태 줄이 이 하나의 값에서 읽습니다. 종료 상태는 컴포저를 절대
비활성화하지 않고, 버튼이 무엇을 제안하는지만 바꿉니다.

| 상태 | 배지 | 예산 바 위의 행 | 전송 슬롯 |
|---|---|---|---|
| idle | 없음 | 없음 | 전송 |
| streaming / executing tool | `STREAMING` (브랜드) | 없음 | **Stop** (error) |
| complete | `COMPLETE` (vault) | Insert · Copy · Retry | 전송 |
| failed / cancelled | `FAILED` (error) | 없음 — 실패 카드는 본문에 | 전송 |

## 6. 화면

| # | 화면 | 종류 | 역할 |
|---|---|---|---|
| 1 | Idle | 주 | 쉬고 있는 패널: 빈 상태, 제안, 컴포저 |
| 2 | Streaming | 주 | 산문과 분리된 툴 활동, 실시간 예산, Stop |
| 3 | Answer | 주 | 인용, 근거 없는 주장 표시, 출처 충돌, 출처 목록 |
| 4 | 삽입 미리보기 | **하위** | 대상, diff, 승인 — Vault에 쓰는 유일한 경로 |
| 5 | 실패 & 복구 | 주 | 살아남은 것, 더 좁은 재시도, 살아 있는 컴포저 |
| 6 | 메모리 설정 | **하위** | 매 질문에 실리는 노트들과 그 비용 |

**하위 화면은 의도적으로 주 화면과 통일되지 않습니다.** 헤더의 왼쪽 그룹을 뒤로가기
버튼과 화면 이름으로 바꾸고, 컴포저를 갖지 않습니다. 그 차이가 "당신은 어떤 작업 안에
있고 여기가 나가는 길"이라는 신호입니다. 이걸 "고치지" 마세요. 하위 화면끼리 일관되어야
하는 것은 패턴입니다 — 뒤로가기, 이름, 상태 배지, 하단의 단일 주요 동작.

## 7. 제품이 걸려 있는 두 규칙

**읽기는 자유롭게, 쓰기는 승인 후에.** 1–3번과 5번 화면은 읽기만 합니다. 답변 화면의
Insert 버튼은 적용이 아니라 이동입니다. 4번 화면을 열고, 거기서 사용자가 실제 줄 diff를
보고 Apply를 누릅니다. 그래서 채워진 브랜드 버튼은 제품 전체에서 정확히 두 곳에만
있습니다 — 전송, 그리고 Apply to note.

**확신보다 증거.** 주장에는 인용 칩이 붙거나, `--fm-pending` 색의 "출처 없음" 표시가
붙습니다. vault 증거와 외부 증거가 어긋나면 양쪽을 출처와 함께 보여줍니다. UI가 조용히
하나를 고르는 일은 없습니다.

## 8. 컴포넌트 매핑

[`src/components/ui`](../src/components/ui)의 각 컴포넌트가 여기서 무엇이 되는지.

| 컴포넌트 | 코필럿에서의 역할 | 필요한 variant |
|---|---|---|
| `bubble` | 질문은 오른쪽 정렬. **답변은 `ghost`** — 400px에서 산문을 말풍선에 넣으면 줄당 글자수가 무너집니다 | `tinted`(사용자), `ghost`(어시스턴트) |
| `marker` | 툴 호출 하나에 한 줄, 그리고 런 구분자. 툴 활동이 산문으로 섞이지 않게 하는 장치 | `default`, `separator` |
| `attachment` | 컨텍스트 칩, 출처 카드, 메모리 행. `state`가 idle → loading → error를 이미 다룸 | `sm`, `horizontal` |
| `alert` | 지속되는 실패와 출처 충돌. 액션 행 포함, 사라지는 토스트는 쓰지 않음 | `destructive`, pending용 `warning` |
| `badge` | 런 상태, `LOCAL`, 인용 번호 | `outline`, 증거 색별 틴트 |
| `message-scroller` | 대화 영역: 스트리밍 중 바닥에 붙고, 독자가 위로 스크롤하면 놓아줌 | viewport + 점프 버튼 |
| `table` | 답변 안에서만, 패널 전체 폭으로. 그 외에는 목록이 됨 | compact |
| `spinner` | 이름이 붙은 활동 옆에서만. 혼자 돌지 않음 | — |
| `button` | Stop과 Apply가 제품 전체에서 유일한 전폭 버튼 | `default`, `outline`, `ghost` |

현재 라이브러리에 없는 것: **diff 뷰**(4번 화면), **예산 바**, 그리고 **컴포저** 자체.

## 9. 미결

- 마크가 흰 아웃라인이라 라이트 Obsidian 테마에서는 어두운 판이 필요합니다. 라이트
  테마는 아직 전혀 그리지 않았습니다.
- 1번 화면은 더 이상 어느 노트가 범위에 있는지 보여주지 않습니다. 후보는 컴포저
  placeholder(`Ask about <note>.md`)이거나, 보낸 질문 아래 꼬리표에 맡기는 것입니다.
  미정.
- 여기서의 메모리는 사용자가 직접 고정해 두는 노트 목록이지 에이전트가 쌓는 기억이
  아닙니다 — 후자는 `docs/PRODUCT.md`에서 비목표로 남아 있습니다. 그게 바뀌면 이 화면도
  함께 바뀝니다.
- 헤더와 하단은 지금 여섯 아트보드에 손으로 복사되어 있습니다. 일곱 번째 화면이
  생기면 공유 셸로 분리하세요.
