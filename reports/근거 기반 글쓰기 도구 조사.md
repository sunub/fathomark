# 근거를 정리하고 선택하는 도구로 글쓰기를 개선한다

Fathomark에 더 필요한 것은 **자료 접근 도구와, 수집한 자료를 글로 바꾸는 명확한 작업 절차**입니다. 지금 그림의 `search_vault`·`read_note`만으로는 누락된 경험을 사용자에게 확인하거나 프로젝트에 연결된 회고를 탐색하기 어렵습니다. 그러나 개요 작성, 비평, 수정까지 전부 별도 도구로 늘리는 것은 추천하지 않습니다. Notion은 자료 범위와 재사용 지침을, Claude Research는 조사 계획과 출처 연결을, Google NotebookLM은 선택한 자료와 작업 메모의 재사용을 지원합니다. 이를 Fathomark에 적용하면 모델 선택 도구는 처음에 약 6개, 이후에도 8개 안팎으로 유지하고 **요구 분석 → 근거표 → 개요 → 초안 → 검증**을 작성 절차로 묶는 구성이 적합합니다. 아래 제품 기능은 공식 자료에서 확인했으며, 제안 도구명은 Fathomark용 설계 이름입니다. 조사 기준일은 2026년 10월 11일이며 이번 작업에서 제품 코드는 변경하지 않았습니다.

💡 **Harness**: 모델 호출, 도구 권한, 실행 한도, 대기와 승인 상태를 관리하는 제품 코드입니다. **도구**는 외부 자료나 사용자 입력에 접근하는 기능이고, **작성 절차**는 확보한 정보를 분석·구성·수정하는 반복 가능한 모델 작업입니다.

## Notion은 검색보다 자료 범위와 반복 절차를 강화한다

Notion Enterprise Search는 Notion과 연결된 업무 자료를 검색하고 답변에 출처를 표시합니다. 웹 또는 업무 자료 검색을 끄거나 특정 소스·페이지·팀스페이스로 범위를 좁힐 수 있습니다. Notion Agent는 현재 페이지와 선택한 블록을 기본 문맥으로 활용하고, 추가 페이지·파일·소스를 지정해 다단계 작업을 수행합니다. 중요한 점은 자료를 더 많이 찾는 기능과 함께 **이번 요청에서 어떤 자료를 사용할지 선택하는 기능**을 제공한다는 것입니다. Fathomark에도 경험 노트, 기업 공개 자료, 문체 참고 자료를 구분하는 범위 선택이 필요합니다. ([Enterprise Search](https://www.notion.com/help/enterprise-search), [Notion Agent](https://www.notion.com/help/notion-agent))

작성에서는 선택 영역의 문법·길이·톤을 수정하고 결과를 수락·폐기·재시도할 수 있습니다. Instructions는 기본 톤·형식 등의 지속 지침이고, Skills는 Improve Writing·Proofread·Reformat처럼 특정 작업에 사용하는 반복 절차입니다. 따라서 Fathomark의 문체 규칙은 기본 문맥으로, 개요 비교·문단 수정·문항 적합성 검토는 작업별 절차로 나누는 편이 자연스럽습니다. **문체를 따라 쓰는 것과 참고 글의 경험을 가져오는 것은 분리해야 합니다.** ([작성 가이드](https://www.notion.com/help/guides/notion-ai-for-docs), [Instructions](https://www.notion.com/help/instructions-for-notion-agent), [Skills](https://www.notion.com/help/create-and-manage-skills))

현재 Research Mode 도움말은 Agent 도움말로 이동하므로 과거 실행 규칙을 현재 기능으로 인용하지 않았습니다. Notion의 내부 도구명·검증 구현은 공개되지 않았고, 기능 설명을 글쓰기 성과 개선의 측정 근거로 해석하지 않습니다.

## Claude와 NotebookLM은 조사 결과를 다음 작업의 재료로 보존한다

Claude Research의 공식 설명은 앞선 검색 결과를 활용한 후속 조사, 여러 관점 탐색, 미해결 질문 확인, 검증 가능한 인용을 강조합니다. 2025년에 공개한 엔지니어링 설계에서는 조사 계획을 메모리에 보관하고, 목표와 범위를 정해 조사 작업을 분배하며, 종합 결과에 필요한 출처를 연결합니다. 평가 항목은 사실 정확성, 인용 정확성, 완전성, 출처 품질, 도구 효율입니다. Fathomark에 가져올 부분은 복수 에이전트 자체보다 **이미 확인한 사실과 남은 질문을 보존하고, 초안의 주장에 출처를 연결하는 책임**입니다. 해당 글은 공개 당시 구조이며 현재 모든 실행의 내부 구성이 같다고 단정하지 않습니다. ([Research 도움말](https://support.anthropic.com/en/articles/11088861-using-research-on-claude-ai), [공개 설계와 평가](https://www.anthropic.com/engineering/multi-agent-research-system))

Google NotebookLM의 Discover Sources는 관련 자료 후보와 설명을 제시했고, Deep Research는 조사 계획을 세워 출처 기반 보고서와 자료를 후속 작업에 재사용하도록 합니다. 공식 업데이트는 검색한 자료를 추가하는 선택을 사용자가 통제한다고 설명합니다. 자료 기반 채팅에서는 인용을 눌러 해당 구절의 문맥을 확인하고, 메모에 표와 인용을 보존할 수 있습니다. Fathomark의 근거표도 한 번 작성하고 버리는 결과보다, 개요·초안·수정에 계속 쓰는 작업 자료로 두는 것이 좋습니다. ([Discover Sources](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-discover-sources/), [Deep Research](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-deep-research-file-types/), [자료 선택 업데이트](https://blog.google/innovation-and-ai/products/notebooklm/better-research-notebooklm/), [인용과 메모](https://support.google.com/gemininotebook/answer/16179559?hl=en))

여기서 사고를 돕는다는 것은 비공개 추론을 보여주거나 `think`라는 이름의 도구를 추가한다는 뜻이 아닙니다. **문항에서 요구하는 능력, 경험 후보별 장단점, 주장을 뒷받침하는 구절, 빠진 사실, 개요 대안**을 사용자와 모델이 함께 확인할 수 있게 만드는 것입니다. 생성한 메모나 모델의 해석을 원래 경험의 증거로 승격시키면 안 됩니다.

## Fathomark는 추가 도구와 실제 제공 상태를 구분해야 한다

현재 저장소에는 Vault 검색·노트 읽기와 Wikipedia 검색·페이지 읽기라는 네 도구 모듈이 구현돼 있습니다. 그러나 실제 플러그인 진입점은 **빈 도구 등록 목록과 가짜 모델 제공자**를 생성합니다. 따라서 네 도구를 실제 설치된 앱에서 사용하는 완성된 흐름으로 설명할 수 없습니다. 문체 선택과 승인 미리보기도 구현돼 있지만 모델이 선택하는 검색 도구와는 다른 기능입니다. 이번 조사는 연결 상태와 설계 범위를 확인했으며 실제 Obsidian 실행이나 성능 측정은 수행하지 않았습니다. ([Vault 도구](/Users/sunub/workspace/fathomark/plugin/src/tools/vault-tools.ts:46), [Wikipedia 도구](/Users/sunub/workspace/fathomark/plugin/src/tools/wikipedia.ts:30), [앱 진입점](/Users/sunub/workspace/fathomark/plugin/src/main.ts:40))

제안하는 도구 구성은 아래와 같습니다. 기존 네 도구에 질문과 연결 문맥 조회를 더하면 초기 구성은 여섯 개입니다. 일반 공개 자료 읽기는 Wikipedia 읽기를 확장·통합하는 방향을 먼저 검토하고, 작업 메모 저장은 기존 실행 상태만으로 부족할 때 추가합니다.

| 도구 | 우선순위·상태 | 입력 → 출력 | 글쓰기에 필요한 이유 |
|---|---|---|---|
| `search_vault` | 기존 모듈 | 질문·허용 범위 → 후보 구절·출처 | 관련 경험 탐색 |
| `read_note` | 기존 모듈 | 노트·제목 → 원문 구절·출처 | 실제 역할과 행동 확인 |
| `search_wikipedia` | 기존 모듈 | 허용 공개 주제 → 자료 후보 | 배경 지식 조사 |
| `read_wikipedia_page` | 기존 모듈 | 이번 검색의 자료 ID → 본문·출처 | 검색 결과의 원문 확인 |
| `ask_user` | 최우선 추가 제안 | 누락 사실·질문·선택지 → 확인 답변·답변 ID | 본인 역할·성과·모순 해결 |
| `get_note_context` | 다음 추가 제안 | 노트·제목·수량 한도 → 구조·연결 노트 후보 | 프로젝트에서 회고·일지로 이동 |
| `read_public_source` | 범위 정의 후 제안 | 사용자 지정·허용 자료 ID → 본문·URL·수집 시각·구절 | 채용 공고와 기업 자료 확인 |
| `save_working_note` | 상태 보존 필요 시 제안 | 근거표·누락·개요 선택 → 저장 ID·상태 | 중단·재개와 수정 시 재사용 |

`ask_user`는 단순 문자열 도구보다 질문 대기와 재개를 포함하는 기능입니다. 기다리는 동안 모델 호출을 멈추고, 사용자의 답변은 노트 출처와 구분해 기록해야 합니다. `get_note_context`는 링크를 근거로 확정하는 기능이 아닙니다. 연결된 노트를 후보로 제공하고 필요한 원문을 읽도록 합니다. `read_public_source`는 사용자가 붙여넣은 공고부터 시작할 수 있으며, 네트워크 읽기를 추가한다면 인증·동적 페이지·PDF 범위를 먼저 결정해야 합니다.

일반 웹 검색은 다음 단계입니다. 현재 ADR0004는 Vault에서만 발견한 이름·표현·경로·메타데이터가 외부 조사 질문에 섞이지 않도록 정합니다. 회사·직무 등 허용된 공개 주제로 검색하고 원문을 읽는 별도 경로를 설계해야 합니다. 공개 회사 정보는 사용자가 그 일을 했다는 증거로 쓰지 않으며, 자료 안의 명령은 사용자 지시로 취급하지 않습니다. 첨부 자료 읽기는 실제 수요가 확인되면 추가하고 CLI는 이번 범위에서 계속 미룹니다. ([외부 조사 경계](/Users/sunub/workspace/fathomark/docs/adr/0004-protect-vault-only-terms-from-research-egress.md:7))

## 글쓰기 품질은 개요 선택과 필수 검증에서 확인한다

먼저 문항·독자·분량·강조할 능력을 작성 조건으로 정리합니다. 다음에는 상황·본인 역할·행동·결과별 근거표를 만들고 확인·해석·누락·충돌을 표시합니다. 이어 같은 경험을 조율 능력 중심과 문제 해결 중심처럼 두 개요로 비교하되 각 개요에 사용할 근거를 연결합니다. 사용자가 선택하면 기존 문체 규칙을 적용해 초안을 만들고, 수정은 대상 문단과 유지할 사실을 지정해 제안합니다. 이는 새로운 외부 도구를 여러 개 만드는 대신 구조화된 작성 결과를 갖는 절차로 시작할 수 있습니다.

**주장 검증은 모델이 선택적으로 호출하는 도구로만 두지 않고 Harness의 필수 단계로 둡니다.** 현재 출처 ID와 인용 요구는 있지만 각 주장의 의미를 원문이 실제로 뒷받침하는지 검증하는 경로는 확인되지 않습니다. 출처 존재·길이·수치 보존은 코드 검사로, 역할·성과의 의미 일치와 문체 예시의 사실 혼입은 별도 검토로 다룹니다. 출처가 붙었다는 이유만으로 참인 문장이라고 판정하지 않습니다. 승인과 적용은 기존 미리보기 및 대상 변경 검사 경로를 재사용합니다. ([출처 처리](/Users/sunub/workspace/fathomark/plugin/src/context/evidence.ts:64), [현재 종료 처리](/Users/sunub/workspace/fathomark/plugin/src/harness/langchain-loop.ts:136), [미리보기와 적용](/Users/sunub/workspace/fathomark/plugin/src/obsidian/insertion-preview.ts:43))

효용 검증에는 근거 없는 역할 생성, 표현이 다른 경험 발견, 공고·문체 자료의 사실 혼입, 문단 수정 시 숫자·의미 보존을 포함합니다. 출처가 있어도 원문보다 과장된 주장도 평가합니다. 같은 문항으로 확장 전후의 경험 발견률, 누락 해결률, 주장·출처 일치, 호출 수와 시간을 비교해야 개선을 판단할 수 있습니다.
