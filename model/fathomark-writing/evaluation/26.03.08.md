## Dispatch SetStateAction 의 주의점

우리가 React을 사용하면 흔히 사용하는 `useState` 을 사용해서 상태를 업데이트하는 로직은 **비동기적으로 스케줄 된 업데이트**라는 것을 주의해야 합니다. 여기서 주의해야하는 표현은 비동기적이라고 하며 Promise, Async 와 같이 비동기적인 작업은 아니라는 것입니다. 스케쥴링을 통해서 비동기적으로 작업이 처리가 되는것과 같이 상태를 업데이트한다는 의미입니다.

```tsx
const [count, setCount] = useState(0);

setCount(1);
console.log(count);
```

위의 로직에서 우리가 기대하는 로그의 출력 값은 `1`이 출력되기를 기대할 것입니다. 하지만 실제로 출력되는 값은 `0`이 출력이 됩니다. 이러한 이유는 무엇일까요? 이는 React가 상태를 업데이트 하는 단계와 연관이 있습니다.

```
- React 의 DOM 업데이트 단계
state → render → commit → DOM
```

위의 단계를 거쳐서 실제 DOM의 상태를 변경하는 과정을 갖는데 React 에서 발생하는 모든 상태 변화를 상태가 변경이 되었을때마다 render 단계로 넘어가게 된다면 어떠한 현상이 나타나게 될까요? 쉴세 없이 리렌더링이 이루어지는 현상이 나타나게 됩니다.

그래서 React 는 상태 업데이트를 `queue` 에 넣고 이후 렌더링 사이클에서 Batching를 수행하여 DOM을 업데이트합니다. 예를 들어,

```tsx
setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);
```

위와 같이 `setCount` 를 여러 번 호출했다고해서 여러번 상태를 업데이트 시키는 것이 아닌 3 작업을 모아 한 번에 처리하고 **한 번 렌더링**하는 과정을 통해서 성능을 최적화 시킵니다. React 18 이후에서는 Auto Batching 이 가능해져서 앞선 예시와 같이 한 번의 렌더링 내에서 여러 상태의 업데이트를 모아서 처리할 수 있게끔 Batching 처리를 수행해 성능을 개선하였습니다. 이외에도 React 의 특징에 대해서 간략하게 설명해보겠습니다.

React는 내부적으로 **Scheduler**가 있습니다. 이 Scheduler 는 브라우저의 메인 스레드가 무거운 렌더링 작업에 의해 장시간 차단되는 것을 막기 위해, 작업들을 언제 실행하고 언제 브라우저에게 제어권을 넘길지 조율하는 역할을 수행합니다.

특히 React 18 이후에는 **Concurrent Rendering(동시성 렌더링)** 작업이 가능해졌습니다.  여기서 주의해야 하는 것은 React의 동시성(Concurrency)은 물리적으로 동시에 실행된다는 의미가 아닙니다. 

여기서 이야기하는 동시성은 Time Slicing 기법을 통해 렌더링 작업을 아주 짧은 단위로 쪼개고 실행의 우선순위를 재조정함으로써 브라우저가 버벅이지 않으면서 동시에 보이게 만드는 것입니다. 동시에 여러  작업을 처리가 가능해진 이유 중 하나는 작업의 **우선 순위**를 기반으로 작업을 일시 **중지**하고 **재개**할 수 있게 되었기 때문입니다.
