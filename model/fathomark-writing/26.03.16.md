## 인프랩과 해당 직무에 지원하게 된 동기를 작성해주세요. 특히 인프런 서비스를 직접 사용해보거나 분석해 보면서, 기술적 혹은 제품적으로 '이 부분은 내가 주도적으로 개선해보고 싶다'고 느꼈던 지점이 있다면 무엇이며, 이를 어떻게 해결해보고 싶은지 구체적으로 서술해주세요.


제가 주도적으로 개선을 해보고 싶다고 느낀 부분은 인프런 courses 의 메인 페이지의 성능을 개선해보고 싶습니다. 이 페이지에서 제가 확인한 가장 큰 문제는 LCP가 너무 크다는 문제와 실제 컨텐츠가 로드되는 부분과 스켈레톤 애니메이션의 위치가 일치하지 않아서 발생하는 CLS 가 잦다는 문제가 있었습니다.

---

인프랩에 지원한 이유는, 인프런이 단순히 기능을 만드는 서비스가 아니라 사용자 경험과 기술적 완성도를 함께 개선해가는 팀이라고 느꼈기 때문입니다. 

인프런 서비스를 직접 사용하고 메인 페이지를 간단히 분석해보면서, 저는 "첫 화면에서 가장 중요한 콘텐츠가 사용자에게 도달하기까지의 경로를 더 짧게 만드는 일"을 주도적으로 개선해보고 싶다고 느꼈습니다.

실제로 Lighthouse 기준 이 페이지는 LCP가 약 5.3초, TBT가 약 2.88초로 측정되었고, 초기 서버 응답은 약 70ms로 짧았습니다. 즉 서버 응답 자체보다, 클라이언트에서 첫 화면을 완성하는 과정이 길다는 점이 더 핵심적인 병목처럼 보였습니다.

조금 더 들여다보면, LCP가 늦는 원인도 단순히 이미지 용량만은 아니었습니다. 기술 블로그를 보면서 S3 Intelligent-Tiering, CloudFront, Lambda@Edge, AVIF 변환 등 인프라 레벨에서 이미지 비용과 전송 효율을 꾸준히 최적화 해왔다는 것을 알 수 있었습니다. 또한 측정 결과에서는 LCP 구성 요소 중 **resource load delay가 약 3초**, **element render delay가 약 1.18초** 수준으로 나타났고, Trace에서도 `FunctionCall`, `RunMicrotasks`, `TimerFire` 비중이 크게 나타났습니다.

저는 이를 보며, 현재 병목은 “이미지가 무겁다”보다 핵심 이미지를 보여주기 전에 초기 JS 실행과 hydration 이후 작업이 오래 이어지는 구조에 더 가깝다고 판단했습니다.

이런 근거를 바탕으로, 저는 인프런 메인 페이지의 개선 방향을 세 가지로 생각했습니다.

첫째, 첫 화면에 꼭 필요한 콘텐츠는 서버에서 더 일찍 확정해 전달하는 방식입니다.  
메인 배너나 첫 화면에 실제로 보이는 강의 카드 일부처럼 사용자가 가장 먼저 인식하는 영역은 Next.js의 SSR/SSG/캐싱 전략을 활용해 초기에 HTML로 전달하고, 반대로 개인화 추천이나 부가 정보는 hydration 이후 혹은 사용자 탐색 시점에 맞춰 점진적으로 로드하는 구조로 개선해보고 싶습니다. 서버 응답은 이미 빠른 편이기 때문에, 결국 체감 속도를 좌우하는 것은 무엇을 첫 화면에 바로 포함시키느냐라고 생각했습니다.

둘째, 초기 화면에서 동시에 렌더링되는 콘텐츠 양 자체를 줄이는 방식입니다.  
인프런처럼 카드형 콘텐츠가 많은 서비스에서는 전체 이미지 수를 줄이는 것보다, 사용자가 실제로 보고 있는 범위 안에서만 DOM과 이미지를 우선적으로 렌더링하는 전략이 더 중요하다고 생각합니다. 그래서 첫 화면 아래의 섹션은 지연 마운트하거나, 긴 리스트 형태의 영역은 가상 스크롤이나 단계적 로딩을 적용해 초기 렌더링 비용을 줄여보고 싶습니다. 이 방식은 LCP뿐 아니라 메인 스레드 부담을 줄여 TBT 개선에도 효과가 있을 것이라고 봤습니다.

셋째, 이미지 자체의 압축을 넘어서 우선순위 전략을 다시 설계하는 것입니다.  
인프랩이 이미 AVIF 변환과 CDN 최적화를 잘 하고 있는 만큼, 다음 단계에서는 “이미지를 얼마나 작게 보내는가”보다 “어떤 이미지를 가장 먼저 발견하고 다운로드하게 만들 것인가”가 더 중요하다고 생각했습니다. 가장 중요한 이미지는 우선순위를 높이고, 아래 영역의 썸네일이나 추천 섹션 이미지는 늦게 발견되도록 설계하면, 같은 리소스 환경에서도 실제 체감 속도를 더 개선할 수 있다고 봤습니다.

앞서 제안한 해결방법의 경우 측정되는 결과만을 기반으로 세운 가설을 바탕으로 세운 해결 방법이기 때문에 만약 실제로 문제를 해결하게 된다면 Datadog·Mixpanel·Lighthouse 같은 도구와 실제 사용자 행동 데이터를 함께 보며 가설을 세우고, 우선순위를 정하고, 점진적으로 검증하는 방식으로 개선을 진행해보고 싶습니다.

예를 들어 사용자가 실제로 어느 섹션까지 탐색하는지, 어떤 요청이 초기 렌더링 경로를 막고 있는지, 어떤 콘텐츠가 첫 화면에서 가장 중요한지를 데이터로 확인한 뒤, 서버 렌더 범위 조정, 초기 JS 축소, 이미지 우선순위 재설계 같은 개선을 단계적으로 적용해보고 싶습니다.



저는 프론트엔드 개발자가 단순히 화면을 구현하는 역할을 넘어, **사용자가 더 빠르고 자연스럽게 제품을 경험하도록 렌더링 경로를 설계하는 역할**도 해야 한다고 생각합니다. 인프런은 이미 인프라와 운영 관점에서 성능 최적화를 꾸준히 해온 서비스이기 때문에, 그 위에서 저는 프론트엔드 관점의 critical rendering path를 더 정교하게 다듬는 방식으로 기여해보고 싶습니다. 사용자에게 가장 중요한 정보를 더 빠르게 전달하고, 실제 비즈니스 지표에도 영향을 줄 수 있는 개선을 직접 주도해보고 싶다는 점이 제가 인프랩과 이 직무에 지원한 가장 큰 이유입니다.

## 개발 과정에서 마주했던 가장 기술적인 도전 과제를 소개해주세요. 단순히 새로운 기술을 도입한 경험보다는, 문제 해결을 위해 고려했던 여러 대안들의 장단점(Trade-off)을 어떻게 분석했고, 왜 최종적인 방식을 선택했는지 '논리적인 근거'를 중심으로 기술해주세요.

이 부분에 대해서 이야기하는 것이 필요할거 같은데 사실 이 부분에 대한 것을 해결하기 위해 가장 적합한 것 경험은 "블로그 초기 진입 속도를 개선하는 과정"에 대한 경험이라고 생각해

이를 해결하기 위해 실제로 내가 수행한 내용은 다음과 같아

초기에 LCP를 줄이기 위해서는 이미지의 크기와 이미지의 포맷을 변경하는 작업을 수행하였다.
이 방법은 물론 효과적인 성능을 보여주었다. 이미지의 크기와 이미지의 포맷 폰트의 크기, 폰트의 포맷은 웹에서 자원의 로드 속도와 파싱과정에서 중대한 사항이기 때문이다.

그래서 woff2, avif 로 포맷을 변경하고 이미지의 크기를 줄이는 방향으로 LCP 를 개선할 수 있었다. 하지만 이 방법은 내 프로젝트에서 완벽한 해결책이 될 수 없었다.

이후에는 CDN을 통해서 문제를 해결하고자 했다. 하지만 이 부분 또한 완벽한 해결책이 될 수 없었다. 왜냐하면 이미 내 이미지와 폰트의 크기는 CDN 을 사용하지 않더라도 큰 차이가 발생하지 않을 정도로 최적화가 이루어져있었고 크지 않은 프로젝트의 크기와 많지 않은 이미지를 포함하고 있었기 때문에 현재 내 블로그에서는 효과적이지도 않고 너무 과한 해결 방법이었다.

내 블로그에서 갖고 있던 또 다른 문제는 Vercel 환경에서 SSG가 아닌 SSR 로 구동하는 개인 블로그를 배포했다는 점이었다. Vercel 이 갖는 Cold Start 라는 문제와 Cpu 자원이 0.6vcpu hobby 플랜에서 사용할 수 있는 자원의 제약이 있었기 때문에 자원로드 과정에서의 최적화가 가장 중요했다.

그래서 다음으로 수행한 작업이 IO 작업 최적화였다. 이 과정에서 Web Worker, Promise.all,  Stream 을 비교하며 문제를 개선하고 했다. 이 과정에서 얻을 수 있는 이점은 Web Worker 의 경우 현재 IO 작업 처리만을 위해서 사용하기에는 용도와 복잡성이 맞지가 않다는 것이었다. 물론 클라우드에 배포되어 있는 파일에 접근할 수 없기 때문에 적합하지 않다는 이유도 있었다.

나머지 두 Stream와 Promise.all 의 성능차이는 크게 차이가 나지 않았다. 오히려 많지 않은 작업량에서는 Promise.all 을 사용하여 IO를 병렬적으로 처리하는 방법이 더 빠른 경우도 있었다. 하지만 결국 Stream 을 선택했는데 이 이유는 대량의 파일을 처리할 경우의 안정성 면에서 Promise.all 보다 더 유리했기 때문이다. Stream 은 Semaphore 를 구현하여 메모리 제한을 두어 동시성 문제를 해결하기에 Promise.all 을 사용하는 방법에 더 유리했기 때문이다. 그렇기 때문에 Stream 을 사용하여 파일들을 읽고 이 후 jsonld 파일로 중요한 정보를 미리 정적인 파일로 만들어 컨텐츠의 로드 속도를 개선시키고자 했다.

하지만 이 또한 완벽한 해결책은 되지 못했다. Vercel 의 Cold Start 는 초기 구동 시간에 시간이 걸리는 작업이었기 때문애 Cron Job 을 이용하여 warming 작업을 실행해주는 것은 hobby plan 에서 불가능했기 때문에 블로그 배포에서 추가적인 비용을 발생하지 않고서는 Vercel에서 이 문제를 해결할 수 없다고 판단 했다.

그래서 무료로 배포가 가능한 선택지중 Amazon ec2 가 있엇다. 이 선택지의 경우 1년간 무료로 사용할 수 있다는 점이 매력적이었고 나에게 부족한 경험 중 하나인 배포의 전체 사이클과 배포후 서비스를 관리하는 측면의 경험을 쌓을 수 있었다는 부분이 장점으로 다가와 문제를 해결하고자 했다. 

그래서 Ec2로 전환하여 기존의 겪던 블로그의 로드 속도가 느리다는 문제는 해결했다. 하지만 아직 LCP 문제가 남아 있었다. 이 문제를 해결하기 위해서는 로드하는 컨텐츠의 수를 줄여야한다고 판단했다. 사용자가 블로그나 다른 사이트에 접속했을 경우의 시나리오를 고려했다. 이 경우 사용자는 한번에 전체 페이지에 대한 정보를 원하지 않다. 오히려 더 빠른 접근성을 선호한다.

그렇기 때문에 가상 스크롤을 사용하여 로드되는 컨텐츠의 수를 제한하고 사용자가 컨텐츠를 더 보고자 하는 의도를 가질 경우에만 추가적인 컨텐츠를 로드하는 방법으로 개선해야 했다. 이 부분은 가상 스크롤을 구현하여 시각적인 영역을 제외하고는 컨텐츠 로드를 하지 않게끔 하여 개선했다.

그리고 또 다른 문제가 남아 있었다. 디자이너, 여기서는 나의 요구사항은 기존의 background-image 를 사용하여 구현하고 있는 background-repeat 을 사용한 애니메이션 효과를 망가뜨리지 않고 싶다는 요구사항이었다. 이 요구사항은 LCP 를 증가시키는 최대 요인이었다. background position 의 경우 CSS에서 파싱과정이 완료가 된 이후에 이미지 로드가 발생하기 때문에 Image 컴포넌트를 사용하여 이미지를 로드하는 과정에서 처리할 수 있는 priority 설정이마 lazy 설정들의 이점들을 전혀 이용할 수 없다는 점이다.

그래서 기존의 요구사항은 지키면서 문제를 해결하기 위해서는 사용자를 속이기로 했다. 페이지가 초기에 로드가 될 경우에는 Next.js 의 Image 컴포넌트를 사용하여 사용자가 즉시 이미지를 보이게끔 했고 이후 2프레임 이후에 , 애니메이션이 충분히 동작할 수 있는 시간을 준 후 자연스럽게 opacity 를 조정하여 애니메이션이 움직일 수 있게끔 개선하였다.

이러한 개선 사항을 통해서 기존의 80점 초반때이던 블로그의 성능을 97점으로 상승 시킬 수 있었다.
