## [미네랄](https://www.acmicpc.net/problem/2933)



## Caching

### memoization + dirty versioning

이 작업에서 수행하고자 한 작업은 스크롤을 수행할때마다 반복하여 수행되는 $O(N)$의 작업을 정말 필요한 경우에만 수행할 수 있게끔 캐싱을 통해서 개선하는 것이었습니다.

이 과정에서 사용된것이 memoization 와 **Dirty Checking** 입니다. 

### Dirty Checking 핵심 구현 방식

1. 스냅샷 비교 방식

데이터를 최초로 로드할 때 원본의 상태를 복사하여 스냅샷으로 보관합니다. 이후 동기화가 필요한 시점에서 현재 데이터의 상태와 보관된 스냅샷을 전수 비교합니다.

2. 상태 플래그 방식
데이터 객체 내부에 version 이나 isDirty 와 같은 변수나 버전의 정수를 사용하여 데이터가 수정되는 순간 이 플래그를 true 로 변경하거나 버전을 증가시켜 동기화 시점에는 이 플래그가 켜진 객체만을 찾아서 업데이트하는 방식을 사용합니다.


## rAF는 Cancel/Requeue 보다는 프레임당 1회 가드 패턴을 사용할 것

웹 브라우저에서 `scroll`, `resize`, `mousemove`와 같은 DOM 이벤트는 브라우저의 화면 갱신 주기보다 훨씬 짧은 간격으로 발생합니다. 이 고빈도 이벤트를 처리하기 위해 rAF를 스케쥴링할때 어떻게 사용하느냐에 따라서 성능 격차가 존재합니다.

### Cancel/Requeue 패턴

이 방법은 이벤트가 발생할때마다 기존의 대기중인 rAF를 취소하고 다시 예약하는 방식입니다. 

```js
if (rafId) {
	cancelAnimationFrame(rafId); 
}
rafId = requestAnimationFrame(update);
```

위와 같이 사용하는 방법은 **프레임 지연 및 기아 현상**을 발생 시킬 수 있습니다. 사용자가 빠르게 스크롤을 연속해서 발생시키면, 브라우저가 다음 프레임을 그리기 위해 콜백을 실행하기도 전에 이전의 대기중인 작업을 제거하기 위해 `cancleAnimationFrame` 을 호출하여 작업을 무효화 시키게 됩니다.

이 과정이 반복되면 스크롤 행위가 완전히 끝날 때까지 화면 업데이트가 단 한 번도 이루어지지 않는 상태, **Stravation, 기아상태**에 빠지게 되어, 이는 화면 갱신 주기를 놓쳐 뚝뚝 끊기는 Jank 의 직접적인 원인이 됩니다.

### 프레임당 1회 가드(Once-per-frame Guard) 패턴의 안정성

불리언(Boolean) 플래그(Flag)를 사용하여, 다가오는 렌더링 사이클에 이미 예약된 작업이 있다면 추가적인 예약을 무시하는 방식입니다.

```js
if (isScheduled) return; // 예약된 작업이 있으면 즉시 종료 (Guard)
isScheduled = true;
requestAnimationFrame(() => {
    isScheduled = false; // 렌더링 직전 콜백 실행 시점에 플래그 해제
    update();
});
```

이 방법은 이벤트가 16.6ms 내에 수십 번 폭주하더라도, 최초의 1회 예약은 취소되지 않으므로 브라우저의 다음 렌더링 사이클 직전에 **반드시 콜백이 실행**됨을 보장합니다. 불필요한 `cancelAnimationFrame` API 호출 비용을 없애 CPU 연산 자원을 절약합니다.

또한 이 방법은 여러 번의 연속된 이벤트가 발생하더라도, 최종적으로 rAF 콜백이 실행되는 단일 시점에서 가장 최신의 DOM 상태만 읽어와서 한 번만 연산하므로 렌더링 파이프라인이 최적화됩니다.

DOM 이벤트 핸들링에서 Cancel/Requeue 방식은 디바운스(Debounce)와 유사하게 동작하여 오히려 필요한 프레임 렌더링을 지연시킬 위험을 내포하고 있습니다. 반면, 상태 플래그를 활용한 '가드 패턴'은 브라우저의 디스플레이 주사율과 정확히 일치하는 스로틀링(Throttling)을 구현하여, 화면 동기화 누락 없이 안정적인 60FPS를 유지하게 하는 프론트엔드 성능 최적화의 표준 아키텍처입니다.
