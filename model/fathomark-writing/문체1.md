## 문서형 데이터 베이스

문서형 데이터 베이스를 사용하는 주된 이유는 스키마의 유연성, 지역성에 기인한 더 나은 성능, 애플리케이션의 데이터 구조와 더 가깝기 때문에 사용합니다.

문서형 데이터 베이스가 스키마의 유연성을 가질 수 있는 이유는 문서형 데이터베이스는 비정규화를 특징으로 갖고 있기 때문입니다. 정규화를 수행한다는 것은 데이터베이스에서 사용할 데이터의 구조와 데이터의 타입들에 대한 구조를 미리 정해놓고 간다는 것을 의미합니다.

문서형 데이터는 정규화를 수행하지 않는 것이 아닌 약하다고 표현해야 합니다. 정규화를 수행할때 데이터의 규칙을 엄격하게 만들어주는 것은 스키마를 강조하기 때문입니다. 문서형 데이터베이스는 스키마리스라고 불리지만 슬제로는 스키마가 있지만 강조하지 않다고 이야기해야 합니다.

엄격하게는 문서형 데이터베이스는 암묵적인 스키마가 존재합니다. 암묵적이라는 것은 강제하지 않는다는 것을 의미합니다. 관계형 데이터베이스의 전통적인 접근 방식인 쓰기 스키마를 강제하지 않습니다. 관계형 데이터베이스의 경우 쓰기 시점 스키마(Schema-on-Write)가 강제되기 때문에 테이블에 작성되어 있는 데이터는 모든 데이터가 스키마를 따르고 있다는 것을 보장합니다.

하지만 문서형 데이터베이스는 읽기 시점 스키마(Schema-on-Read)를 따릅니다. 데이터의 구조는 암묵적인 구조를 가지고 있지만 문서형 데이터베이스의 데이터를 읽을 경우에는 쿼리문에서 읽고자 할 경우 문서 데이터베이스의 구조를 해석하고 따라야 한다는 특징을 갖고 있습니다.

### 애플리케이션의 데이터 구조와 가깝다는 것의 의미

애플리케이션 데이터의 구조와 가깝다는 것의 의미는 객체를 있는 그대로 저장하기 때문입니다. 또한 현대적인 프로그래밍 언어는 데이터와 행위를 Object(객체) 단위로 관리하고 있습니다. 문서형 데이터 베이스의 경우 이와 같이 객체의 계층 구조를 그대로 유지하며 저장할 수 있다는 특징을 갖고 있기 때문에 애플리케이션의 구조와 유사하다는 표현을 사용합니다.

## 지역성

지역성(Locality)은 하드웨어 간의 속도 차이 그 자체를 의미하는 것이 아니라, "프로그램이 데이터에 접근할 때 가지는 통계적 특성"을 말합니다.

컴퓨터 아키텍처는 이 지역성을 활용하기 위해 **메모리 계층 구조**를 가집니다. CPU와 가까운 캐시나 RAM은 빠르지만 비싸고 용량이 적으며, HDD/SSD는 느리지만 용량이 큽니다. 지역성이 높은 코드를 작성하면 데이터가 느린 저장소(HDD/SSD)에서 빠른 저장소(RAM/Cache)로 미리 옮겨져 실행 속도가 비약적으로 향상됩니다.

RDBMS는 데이터를 정규화하여 관리합니다. 이때 특정 데이터를 빠르게 찾기 위해 **B-Tree 인덱스**를 사용하며, 이는 저장소의 **공간적 지역성**을 극대화하도록 설계되었습니다.

```sql
-- Users 테이블
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    name VARCHAR(50)
);

-- Orders 테이블 (User와 분리되어 저장됨)
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    user_id INT,
    product_name VARCHAR(100),
    FOREIGN KEY (user_id) REFERENCES users(user_id)
);

-- 데이터 조회 (JOIN 사용)
SELECT u.name, o.product_name 
FROM users u 
JOIN orders o ON u.user_id = o.user_id 
WHERE u.user_id = 1;
```

B-Tree 인덱스는 인덱스 정보들을 **페이지(Page) 단위**로 묶어서 관리합니다. 사용자가 특정 ID를 찾을 때, DB는 해당 ID 근처의 인덱스 정보를 한 번의 디스크 읽기로 대량 로드하여 탐색 효율을 높입니다. 위의 쿼리문에서는 FK 을 사용하여 데이터의 JOIN 과정의 성능을 개선하고 합니다. 하지만 이 부분에서는 FK를 사용하더라도 어쩔 수 없는 성능 저하가 발생할 수 있습니다.

JOIN이 느린 이유는 전체 데이터를 탐색하기 때문이 아니라, 서로 다른 테이블, 물리적으로 떨어진 위치의 데이터를 참조하기 위해 디스크의 이곳저곳을 찔러야 하는 무작위 접근(Random I/O)이 발생하여 지역성이 깨지기 때문입니다.

인덱스(B-Tree)는 메모리에 캐싱되어 있거나 물리적으로 잘 정렬되어 있어 매우 빠르게 탐색합니다. 여기서 결과로 얻는 것은 데이터가 저장된 '물리적 주소(RID 또는 PK)'입니다. 인덱스에서 얻은 주소를 따라 실제 데이터가 담긴 데이터 페이지(Page)를 읽어와야 합니다. 이때, 데이터들이 디스크 상에 순차적으로 있지 않고 여기저기 흩어져 있다면, CPU는 매번 다른 물리적 위치로 "점프"해야 합니다. 그렇기 때문에 FK 를 사용한다고 해서 무작위 접근을 개선하여 성능을 개선할 수는 없는것입니다.

문서형 DB는 관련 있는 데이터를 하나의 객체로 묶는 **임베딩(Embedding)** 방식을 통해 저장소 지역성을 극대화합니다.

```json
{
  "_id": 1,
  "name": "Choi",
  "orders": [
    { "order_id": 101, "product_name": "Mechanical Keyboard" },
    { "order_id": 102, "product_name": "Wide Monitor" }
  ]
}
```


사용자 정보와 주문 내역이 물리적으로 **하나의 문서(Block)** 내에 인접하여 저장됩니다. 데이터를 조회할 때 별도의 JOIN 작업 없이 한 번의 순차적 접근(Sequential I/O)만으로 연관된 모든 정보를 가져옵니다. "함께 쓰이는 데이터는 물리적으로 가깝게 둔다"는 **공간적 지역성**의 원리를 데이터 모델링 단계에서 직접 구현한 것입니다.

**문서형 데이터베이스**는 데이터 임베딩을 통해 연관된 객체 전체를 물리적으로 인접한 공간에 저장합니다. 이를 통해 JOIN 과정 없이 단일 문서를 읽는 것만으로 필요한 데이터를 모두 확보하여, 저장소의 **공간적 지역성**을 극한으로 활용하고 탐색 시간을 획기적으로 단축합니다.

---

다대일과 다대다 관계를 표현할 때 관계형 데이터베이스와 문서 데이터베이스는 근본적으로 다르지 않다. 관계형 데이터베이스에서는 특정 데이터를 참조하기 위해서 관련 항목은 고유한 식별자로 참조를 수행하는데 이때 이 고유한 식별자를 **외래 키(Foreign Key, FK)** 라고  정의하고 문서형 데이터베이스에서는 **문서 참조(document reference)** 라고 정의합니다. 이 식별자는 조인이나 후속 질의를 사용해서 읽기 시점에서 확인하여 사용됩니다.

어떤 시점에서 발생하는 기록하는 문서 데이터베이스를 사용하는 분석 애플리케이션에서는 다대다 관계가 결코 필요로 하지 않는다.

다대다 관계에서 문서형 모델은 결코 어울린다고 할 수 없다.

상호 연결이 많은 데이터의 경우 문서 모델은 곤란하지만 관계형 모델은 무난하며 그래프 모델은 매우 자연스럽다.

스키마리스라고 정의하지만 엄격하게는 쓰기 스키마와 반대되는 읽기 스키마를 가지고 있다고 이야기해야만 한다. 관계형 데이터베이스의 전통적인 접근 방식으로 스키마는 명시적이고 데이터 베이스는 쓰여진 모든 데이터가 스키마를 따르고 있음을 보장한다. 읽기 쓰기마의 경우 데이터 구조는 암묵적으로 데이터를 읽을 때만 해석이 된다.
