## 저장소와 검색

가장 기본적인 수준의 데이터베이스에서는 두 가지 작업을 수행합니다. 어떤 데이터를 받으면 데이터를 저장하고 나중에 그 데이터를 요청하여 다시 데이터를 제공한다는 원칙을 수행합니다. 데이터베이스 작업을 수행할 경우 저장소 엔진을 직접 구현하기보다는 사용 가능한 여러 저장소 엔진 중 애플리케이션에 가장 적합한 엔진을 선택하는 작업이 반드시 필요합니다.

이를 위해서는 저장소 엔진이 내부에서 수행되는 작업에 대한 대략적인 이해가 필요합니다. 특히 트랜잭션 작업 부하에 맞춰 최적화된 엔진 간에 큰 차이가 있기 때문에 트랜잭션의 처리나 분석 방법에 대해서는 더 잘 파악할 필요가 있습니다.

```sh
#!/bin/bash

db_set() {
	echo "$1,$2" >> database
}

db_get() {
	grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}
```

우선 저장소 엔진에서 값을 저장하고 검색하는 방법에 대해서 이야기해보겠습니다. 우선 가장 단순하지만 효과적인 저장 방식인 **로그(Log)** 에 대해서 이야기해보겠습니다. 로그는 믿기지 않을 정도로 유용합니다.

```sh
db_set 42 '{ "name": "San Francisco", "attractions" : ["Exploratorium"] }'

db_get 42
'{ "name": "San Francisco", "attractions" : ["Exploratorium"] }'
```

우선 위의 코드의 결과물에 대해서 이야기해보겠습니다. 위의 로그는 굉장히 유용하지만 데이터베이스에 많은 레코드가 있으면 성능이 매우 좋지 않습니다. 매번 키를 찾을 때마다 키가 있는지 찾기 위해 전체 데이터베이스 파일을 처음부터 끝까지 스캔해야 하기 때문입니다.

실제 오늘날의 많은 데이터베이스들은 이러한 특정 키의 값을 찾기 위해 다양한 최적화 방법을 사용하는데 이 중 특정 키를 빠르게 찾기 위해서 **색인(Index)** 를 활용합니다.

데이터베이스는 색인의 추가와 삭제를 허용합니다. 색인의 추가의 경우 추가할 수 있는 최대 색인의 수를 제한해놓고 있지 않습니다. 하지만 무분별한 색인의 추가는 데이터베이스의 쓰기 속도를 느리게 만든다는 문제가 발생합니다.

색인의 추가는 데이터베이스의 내용에는 어떠한 영향을 주지 않고 단지 질의 성능에 영향을 주기 때문에 적절한 색인의 추가는 질의 속도를 향상시킵니다. 하지만 쓰기 작업시마다 생성되어 있는 색인의 갱신이 필요하기 때문에 오버헤드가 발생하기 때문입니다.

## 해시 색인

키-값 데이터를 색인한다고 가정을 할 경우 가장 먼저 떠올릴 수 있는 자료구조는 해시 테이블을 떠올릴 것입니다.

단순히 파일에 데이터를 저장소를 구성한다고 가정해볼경우 가장 간단한 색인 전략의 경우 키를 데이터 파일의 바이트 오프셋에 매핑해 인메모리 해시 맵을 유지하는 전략입니다. 

![[Pasted image 20260530110927.png]]

파일에 새로운 키-값 쌍을 추가할 때마다 방금 기록한 데이터의 오프셋을 반영하기 위해 해시맵도 갱신해야 합니다. 값을 조회하기 위해서는 데이터 파일에서 오프셋을 찾아 해당 위치를 구하고 값을 찾는 방법을 사용하게 됩니다.

지금까지 이야기하고 있는 데이터베이스의 방향은 로그를 파일 끝에 데이터를 계속 Append-only 하는 방향으로 작업을 수행하는 방향의 데이터베이스를 이야기하고 있습니다. 이러한 데이터베이스 중 대표적으로 Bitcask 가 있습니다. 

**Bitcask** 는 해시 맵을 전부 메모리에 유지하기 때문에 사용 가능한 램에 모든 키가 저장된다는 조건을 전제로 고성능으로 읽기, 쓰기를 보장합니다. 앞선 방식과 같이 디스크에 키와 값을 갱신하는 방법을 사용하게 될 경우 결국 디스크의 공간이 부족해지는 현상이 발생하게 됩니다. 이 경우 개선하는 방법이 **세그먼트(Segment)** 로 로그를 나누는 방식이 좋은 해결책입니다. 

![[Pasted image 20260530113001.png]]

특정 크기에 도달하게 될 경우 세그먼트 파일을 닫고 새로운 세그먼트 파일, 일정 크기로 잘라서 별도의 파일들로 나누어 저장하고 관리하는데, 이렇게 분할된 각각의 데이터 파일 블록을 세그먼트라고 부릅니다. 그럼 이 후 세그먼트 파일들에 대해 컴팩션을 수행할 수 있습니다. 컴펙션이란 로그에서 중복된 키를 버리고 각 키의 최신 갱신 값만 유지하는 것을 의미합니다.

세그먼트의 경우 파일로 관리가 되기 때문에 이미 작성된 세그먼트의 경우 쓰여진 후에는 절대 변경할 수 없기 때문에 병합할 세그먼트는 새로운 파일로 만듭니다. 고정된 세그먼트의 병합과 컴팩션은 백그라운드 스레드에서 수행할 수 있습니다. 컴팩션이 백그라운드에서 수행되기 때문에 읽기 작업을 수행할 경우 이전의 작성되어 있는 세그먼트 파일을 기반으로 값을 반환하기 때문에 중단되지 않고 작업을 수행할 수 있습니다.

![[Pasted image 20260530113819.png]]

병합 과정이 끝난 이후에는 읽기 요청은 이전 세그먼트 대신 새로 병합한 세그먼트를 사용하게끔 전환합니다. 병합 이후의 이전의 세그먼트의 경우 이전의 파일을 삭제하기만 하면 됩니다. 이러한 작업 이후에 병합 과정을 통해 세그먼트의 수를 적게 유지할 수 있기 때문에 조회시의 많은 해시 맵을 확인할 필요가 없기 때문에 질의 성능을 개선할 수 있습니다.

하지만 이러한 방식의 데이터베이스에서는 다음과 같은 한계를 갖고 있습니다.

- 레코드 삭제
- 고장 복구
- 부분적으로 레코드 쓰기
- 동시성 제어
