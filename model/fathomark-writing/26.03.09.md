## [오등큰수 성공](https://www.acmicpc.net/problem/17299)

스택 문제의 핵심은 결국 어떻게 조건을 좁히는지에 관한 것이 중요합니다. 이 조건을 좁힌다는 것은 다음으로 나아가기 위한 값들을 최소화하는 것입니다.

이 문제를 예시로 생각해보겠습니다. 이 문제에러 중요한 조건은 `F[i]` 의 값과 `index` 의 위치입니다. 현재 인덱스보다 더 오른쪽 위치에 있는 수 들중 가장 가까운 `F[i]` 값을 찾는 것이 이 문제의 핵심 조건입니다.

이 문제를 해결하기 위해서는 조건을 반대로 생각해봤어야 합니다. 인덱스를 역으로 탐색한다고 할 경우 이 문제의 조건은 다음과 같이 변경됩니다.

"현재 까지 탐색한 값들 중 현재 인덱스보다 `F[i]`가 작거나 같은 값들을 제외한다." 라는 조건으로 변경이 됩니다. 이 조건에 맞춰 stack 에 담긴 값들을 제외하면 stack 에서는 현재 조건에 부합한 최소한의 수만 담겨 있기 때문에 이 문제를 해결할 수 있습니다.

결과적으로 스택에서 쓸모없어진 값들을 `pop`으로 날려버리고 나면, 스택에는 **"위치상으로 더 멀리 있으면서 등장 횟수는 압도적으로 커서, 언젠가 누군가의 오등큰수가 될 가능성이 남아있는 수"** 들만 남게 됩니다. 

## Preload 는 만능이 아니다

```html
<link rel="preload" />
```

`preload`는 브라우저에 특정 리소스가 현재 문서에서 곧 필요하다는 점을 미리 알려, 해당 리소스를 **조기에 가져오도록 유도하는 메커니즘**입니다. 이는 브라우저가 기본적으로 수행하는 리소스 발견 및 로딩 스케줄링 과정에 개발자가 개입할 수 있는 수단이기도 합니다.

이 기능은 폰트, LCP 후보 이미지, 첫 화면에서 반드시 필요한 핵심 비주얼처럼 **초기 렌더링에 직접 영향을 주는 리소스**에 매우 유용할 수 있습니다. 하지만 이를 과도하게 사용하면 오히려 성능에 불리하게 작용할 수도 있습니다.

네트워크 자원은 제한되어 있기 때문에, 너무 많은 리소스를 preload하면 CSS, 폰트, 스크립트, 이미지 등 다른 중요한 리소스와 **초기 네트워크 자원을 두고 경쟁**하게 될 수 있습니다. 특히 느린 네트워크 환경이나 저사양 모바일 환경에서는 이러한 판단이 성능에 더 큰 영향을 줄 수 있습니다.

따라서 preload는 **다른 모든 리소스보다 무조건 먼저 받아오게 만드는 마법 같은 기능**이라기보다는, 현재 페이지에서 곧 필요할 중요한 리소스를 **더 일찍 발견하고 요청하도록 돕는 힌트**로 이해하는 것이 정확합니다.

잘못 사용된 preload는 다음과 같은 문제를 만들 수 있습니다.

- 실제로 더 중요한 CSS, 폰트, 스크립트 등과 초기 네트워크 자원을 두고 경쟁함
- 현재 페이지에서 실제로 사용되지 않는 리소스를 미리 다운로드함
- 특정 뷰포트나 조건에서 필요하지 않은 리소스를 먼저 요청함
- 현재 화면과 직접적으로 관련 없는 리소스를 앞당겨 요청함

그렇다면 preload는 언제 사용하는 것이 적절할까요? 일반적으로 다음과 같은 경우에 고려할 수 있습니다.

- **LCP 후보 이미지**
- **첫 화면에서 반드시 표시되어야 하는 핵심 비주얼**
- **CSS를 통해 발견되어 상대적으로 늦게 요청될 수 있는 배경 이미지**
- **현재 페이지에서 실제로 사용되는 소수의 핵심 리소스**

결국 preload는 **많이 사용하는 것이 중요한 기능이 아니라**, 현재 페이지의 초기 렌더링에 직접적인 영향을 주는 **소수의 핵심 리소스에 한정해 신중하게 사용하는 것이 중요합니다.**

## Avif 포맷의 함정

`Avif` 포맷은 웹에서 사용하는 이미지의 압축 포맷 중에서 이미지의 압축률이 높으면서도 이미지의 원본 이미지의 품질을 유지할 수 있는 좋은 이미지 포맷입니다. 그래서 저는 압축율도 높고 이미지의 품질이 좋기 때문에 아무런 의심 없이 이 이미지 포맷을 사용했습니다.

하지만 이 `Avif`로 인해서 `slow 4g` 환경에서늬 테스트를 수행할 경우 이미지의 위치에 검은색 배경이 짧은 시간 나타났다가 사라지는 현상이 반복되는 것을 확인할 수 있었습니다. 

하지만 이번 작업에서 얻을 수 있었던 것은 **파일 크기가 더 작다고 해서 실제 표시가 빠르지 않다는** 것이었습니다.

이미지가 웹 화면에 표현되기 위해서 필요한 작업들은 다음과 같습니다.

$$다운로드 + 디코드 + GPU 업로드 + 래스터 + 컴포지트$$ 
위의 작업들의 결정으로 인해서 자원의 크기가 충분히 작다고 하더라도 브라우저가 화면에 그려내는 작업은 느려질 수 있다는 것입니다. 

`AVIF`는 일반적으로 압축 효율이 좋지만, 다른 이미지 포맷보다 디코딩 비용이 더 클 수 있습니다. 특히 알파 채널이 있는 이미지나, 현재 저의 경우는 CSS background를 사용했는데 CSS background와 같은 큰 영역에 반복적으로 페인팅·합성이 발생하는 배경 텍스처에서는 일부 환경에서 성능 부담이 더 두드러질 수 있습니다.

이러한 `Avif`의 특징이 섞이면 용량이 적지만 웹의 화면에 그려내는 것은 파일 크기는 크지만 포맷은 더 유리한 `Webp` 보다 더 느린 속도로 화면에 그려질 수 있습니다.


`WebP` 의 경우 파일 크기가 조금 더 커도 브라우저의 디코드 경로가 상대적으로 가볍고 안정적이어서, 반복 배경이나 투명 레이어처럼 즉시 화면에 그려져야 하는 UI 자산에서는 더 빠르게 그려질 수 있습니다. 이는 다음에 설명하는 `WebP`의 특징과 연관이 있습니다.

- 디코드 비용이 AVIF보다 가벼운 경우가 많습니다.
- 브라우저 지원과 렌더링 경로가 더 성숙해서 예측 가능성이 높습니다.
- 투명 배경이 있는 UI 자산, 장식 레이어, 반복 텍스처에서 안정적으로 동작하는 편입니다.
- background-image, repeat-x, 애니메이션과 같이 페인트가 자주 일어나는 상황에서 artifact가 덜 생길 수 있습니다.

이러한 특징으로 인해서 `WebP`가 `AVIF`에 비해 화면에 올리기까지의 총 비용이 더 낮았기 때문에 저의 경우 `WebP` 를 사용하는 것이 UX를 더 향상 시킬 수 있는 좋은 해결책이 될 수 있었습니다.
