## [전력난](https://www.acmicpc.net/problem/6497)

이 문제는 **스패닝 트리**를 활용하여 문제를 해결해야 했습니다. 하지만 이 문제를 해결할 경우에 이 **스패닝 트리** 에 대해서 명확하게 인지하고 풀지는 못했습니다.

단지 주어진 정보에서 비용이 작은 순으로 정렬을 수행한 후 정렬되어 있는 순서대로 트리를 구성해나가지만 문제의 조건이 모든 트리가 연결되어 있는 상태를 유지해야 한다는 조건이 있었기 때문에 이 조건을 지키면서 문제를 해결하기 위해서 **Union Find** 를 사용하여 순환이 발생하지 않았을 경우에만 트리를 연결시키는 방식을 사용하여 문제를 해결하였습니다. 이 방법이 **Kruskal's algorithm** 를 활용하여 문제를 해결하는 방법이었습니다. 

### Spnaning Tree 란?

스패닝 트리는 연결 그래프에서 모든 정점을 포함하면서 사이클이 없도록 구성한 부분 그래프를 의미합니다. 이 스패닝 트리는 특정 자료구조를 의미하는 것이 아닌 그래프 이론에서의 개념, 구조라는 것을 기억해야 합니다.

즉, 배열처럼 구현되는 구조가 아니라 "그래프의 부분 집합이 만족해야 하는 조건"이라는 것을 짚고 넘어가면 될 것 같습니다.

그리고 위에서 제가 사용한 방법의 경우 **최소 스패닝 트리**를 구하는 방법이었습니다. 스패닝 트리의 조건을 만족하는 트리의 경우 한 가지 트리에서도 여러가지가 존재할 수 있고 이 스패닝 트리에서 최소의 가중치의 합을 갖게끔 하는 것이 **크루스칼 알고리즘** 입니다.

## JSON.parse 의 문제점

JSON(JavaScript Object Notation) 은 오늘날 데이터를 전송하기 위하여 널리 사용이 되는 **데이터 교환 포맷**입니다. 여기서 주의해야하는 점은 JSON 을 **데이터 타입**이라고 표현해서는 안된다는 것입니다. 

데이터 타입에 해당하는 것은 다음과 같습니다. 

- `string`
- `number`
- `boolean`
- `object`
- `array`

데이터 타입와 같이 정의가 불가능하기 때문에 데이터 타입이라고 정의해서는 안됩니다. 우리가 흔히 보는 JSON은 다음과 같습니다. 

```json
[
  {
    "userId": 1,
    "id": 1,
    "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
    "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum\nreprehenderit molestiae ut ut quas totam\nnostrum rerum est autem sunt rem eveniet architecto"
  }
]
```

위의 JSON 코드는 속성-값 쌍, 배열 자료형 또는 기타 모든 시리얼화 가능한 값 또는 키-값 쌍으로 이루어진 데이터 오브젝트로 표현이 될 수 있습니다. 위와 같이 우리가 흔히 사용하는 언어에서는 JSON을 위와 같이 `object`로 파싱을 사용합니다.

하지만 JSON을 전송할 경우에는 기존의 `object` 타입의 객체를 `string` 타입으로 전송하여 사용됩니다. 문자열로 변환이 되는 이유는 문자열이 네트워크는 바이트 단위로 전송할 수 있고 텍스트는 가장 호환성이 높기 때문에 문자열의 형태로 전송됩니다.

JSON을 사용할 경우의 문제점이 이러한 직렬화 과정을 거쳐서 문자열로 전달된 데이터를 애플리케이션에서 사용하기 위하여 파싱하는 과정에서 발생합니다.

## Infinite Scroll 의 몰락

Infinite Scroll의 문제점은 서비스의 가치, 사용자가 정보를 탐색하는데 유의미한 효과를 주지 못했다는 점에서 발생합니다. 틱톡이나 트위터와 같이 사용자가 특정한 컨텐츠를 탐색하는 목적이 없이 서비스를 이용하는 경우에는 Infinite Scroll이 유용합니다. 

하지만 제품 사이트나, 특정 정보를 제공하는 서비스에서는 Infinite Scroll을 사용하여 컨텐츠를 제공하는 방법은 오히려 단점이 된다는 연구결과가 있었습니다. Infinite Scroll 은 사용자의 집중력을 분산 시켜서 컨텐츠에 몰입할 수 없게 한다는 단점이 존재 했습니다. 이로 인해서 CPC(클릭당 비용)의 전년 대비 감소가 발생하는 기업 또한 생기기 시작했습니다.

이러한 사업적인 가치 이외에도 Infinite Scroll 은 기술적인 단점이 존재합니다.

### 스크롤의 위치를 복원하는 과정이 복잡하다.

Infinite Scroll 은 JavaScript를 통해서 동적으로 주입되는 컨텐츠이기 때문에 브라우저가 사용자가 이전의 탐색하던 스크롤의 위치를 기억하지 못합니다. 그렇기 때문에 사용자에게 연속되는 경험을 제공하기 위해서는 직접 이전의 스크롤의 위치를 계산하여 기록한 후 `scrollTop`을 사용하여 다시 복귀 시켜줘야 한다는 단점이 존재합니다.

이 경우 아이템 높이가 가변적인 경우 복원된 위치가 미묘하게 어긋나게 되기 떄문에 (이 문제는 해결하기 정말 어려운 부분) 사용자 경험을 저하시키는 문제가 발생합니다.

### 뒤로가기가 까다롭다.

SPA에서는 `history.pushState()`를 통해서 URL을 업데이트하지 않습니다. 업데이트가 이루어지지 않으면 브라우저에서 뒤로가기 버튼을 눌렀을 경우 이전 컨텐츠로 되돌아가는 것이 아닌 사이트를 벗어나게 되어버립니다. URL을 업데이트하더라도 `popstate` 이벤트 핸들링, 스크롤 위치 캐싱, 데이터 재요청 여부 판단 등 신경 써야 할 것이 한두 가지가 아니라는 복잡성을 야기하게 됩니다.

### DOM 비대화와 메모리

DOM 비대화와 메모리를 관리하는 방법은 사용자가 현재 보고 있는 부분만 렌더링하고 관리한다는것이다. 

1. **viewport에 보이는 것만 렌더**하고
2. `requestAnimationFrame`으로 **여러 프레임에 걸쳐 점진 렌더**하며
3. **스크롤 위치를 화면 전환 간에도 보존**한다.
4. 또, **중요하지 않은 렌더링은 `requestIdleCallback`으로 idle 시간에 수행**해 체감 성능을 올린다.

결론은 DOM의 개수를 줄여야 한다는것, 이 기준은 사용자가 현재 보고 있는 스크롤을 기준으로, 또한 데이터의 상한을 제한해야 한다는 것, 무한은 없고 특정 개수의 데이터만 저장하여 관리한다는 것이다. 
### 대안 패턴 비교

무한 스크롤을 대체할 수 있는 패턴들과 그 trade-off를 정리하면 다음과 같다.

|패턴|장점|단점|적합한 맥락|
|---|---|---|---|
|**Pagination**|위치 감각 유지, SEO 우수, 접근성 좋음|페이지 전환 마찰, 사용자 불만 높음|검색 결과, 관리자 목록|
|**Infinite Scroll**|마찰 제거, 체류 시간 증가, 모바일 친화적|위치 상실, CLS 악화, 접근성 파괴|소셜 피드, 이미지 갤러리|
|**Load More 버튼**|사용자 제어, CLS 우회, 접근성 양호|클릭 필요, 초기 구현은 단순하지만 스크롤 복원이 어려움|이커머스, 블로그 목록|
|**Hybrid** (자동 N회 로딩 후 Load More)|초반 마찰 제거 + 후반 제어|구현 복잡도 증가|콘텐츠 양이 많은 목록|
|**Virtualized Infinite Scroll**|메모리/DOM 효율적, 대량 데이터 처리|SSR 호환성, 가변 높이 처리 복잡, 접근성 문제 동일|대시보드, 데이터 테이블|
