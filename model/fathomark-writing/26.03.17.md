## 인프랩과 해당 직무에 지원하게 된 동기를 작성해주세요. 특히 인프런 서비스를 직접 사용해보거나 분석해 보면서, 기술적 혹은 제품적으로 '이 부분은 내가 주도적으로 개선해보고 싶다'고 느꼈던 지점이 있다면 무엇이며, 이를 어떻게 해결해보고 싶은지 구체적으로 서술해주세요.

인프런에 지원한 이유는, 인프런이 단순히 강의를 판매하는 서비스를 넘어 더 많은 사람이 배우고 성장할 수 있도록 학습 경험 전체를 설계하는 플랫폼이라고 느꼈기 때문입니다. 특히 인프랩 개발팀이 추구하는 “적절한 시기에 적합한 도구로 고객 문제를 해결한다”는 방향에 공감했습니다. 저 역시 프론트엔드 개발자로서 화려한 기술보다, 사용자가 실제로 마주하는 문제를 더 자연스럽고 신뢰감 있게 해결하는 일을 중요하게 생각해왔기에 인프랩에서 그 방향으로 기여하고 싶어 지원했습니다.

인프런 서비스를 직접 사용하고 메인 페이지를 분석하며 가장 먼저 개선해보고 싶었던 부분은 첫 화면에서 핵심 콘텐츠가 사용자에게 도달하기까지의 시간을 줄이는 일이었습니다. 메인 페이지는 사용자가 인프런을 처음 인식하고 카테고리와 콘텐츠를 빠르게 이해하는 첫 접점이기 때문에, 이 구간이 늦어질수록 탐색 의지와 서비스 신뢰 형성도 함께 늦어진다고 보았습니다. 저는 첫 화면 렌더링 성능과 초기 콘텐츠 노출 경험을 개선하는 작업을 여러 번 수행해왔기에 이 지점을 더 먼저 보게 되었습니다.

Lighthouse 기준 메인 페이지의 LCP는 약 5.3초, TBT는 약 2.88초였고 초기 서버 응답은 약 70ms로 짧았습니다. 또 LCP 요소에서 resource load delay와 element render delay 비중이 컸고, Trace에서도 FunctionCall, RunMicrotasks, TimerFire 비중이 높았습니다. 이를 바탕으로 서버 응답보다 초기 JS 실행과 hydration 이후 작업이 첫 화면 완성의 더 큰 병목이라고 판단했습니다. 인프런이 기술 블로그를 통해 CloudFront, Lambda@Edge, AVIF 변환 등 인프라 레벨 최적화를 꾸준히 진행해온 점을 고려하면, 현재 개선 여지는 단순 전송 효율보다 초기 렌더링 우선순위와 클라이언트 작업량에 더 있다고 보았습니다.

그래서 메인 배너와 첫 카드 영역처럼 viewport 안에서 바로 보이는 콘텐츠는 서버에서 더 이르게 확정해 전달하고, 개인화 추천이나 하위 섹션은 이후에 점진적으로 로드해 초기 렌더링 비용을 줄여보고 싶습니다. 또한 첫 화면 아래 섹션은 후순위로 마운트하거나 단계적으로 렌더링해 초기 DOM 수와 JS 실행량 자체를 줄이고 싶습니다. 

물론 이 판단은 외부에서 관찰한 측정 결과를 바탕으로 세운 가설이기 때문에, 실제로는 Datadog 같은 도구와 사용자 행동 데이터를 함께 보며 실제 병목을 확인한 뒤, 서버 렌더 범위 조정, 초기 JS 축소, 렌더링 우선순위 재설계 중 비용 대비 효과가 큰 항목부터 단계적으로 적용해 인프런의 탐색과 학습 시작 경험을 개선하고 싶습니다.

## 개발 과정에서 마주했던 가장 기술적인 도전 과제를 소개해주세요. 단순히 새로운 기술을 도입한 경험보다는, 문제 해결을 위해 고려했던 여러 대안들의 장단점(Trade-off)을 어떻게 분석했고, 왜 최종적인 방식을 선택했는지 '논리적인 근거'를 중심으로 기술해주세요.

제가 가장 기술적으로 깊게 고민한 과제는 "최신 글 목록의 스크롤 경험을 개선한 일"입니다. 기존 구현은 빠른 스크롤에서 콘텐츠가 비어 보이거나 늦게 나타났고, 추가 로드가 한 번에 몰리면서 탐색 흐름을 끊고 있었습니다. 그래서 저는 이를 단순한 렌더링 성능 문제가 아니라, 사용자가 끊김 없이 자연스럽게 콘텐츠를 탐색할 수 있도록 만드는 사용자 경험의 문제로 정의했습니다.

개인 프로젝트였기 때문에 검증된 패키지로 증상을 빠르게 완화하는 것보다, 기존 구조에서 어떤 조건이 문제를 만드는지 직접 이해하고 설명할 수 있는 상태를 만드는 것을 더 중요하게 봤습니다. 당시 문제는 렌더 범위 계산, loadMore 중복 호출, 가변 높이 측정 오차가 복합적으로 얽혀 있어 단순 교체만으로는 원인을 파악하기 어렵다고 판단했고, 그래서 패키지로 바로 대체하기보다 기존 구조를 분해해 근본 원인을 확인하는 방향을 선택했습니다.

비교한 대안은 두 가지였습니다. 첫 번째는 기존 sentinel component 기반 구조를 유지한 채 데이터 로드 시점만 조정하는 방법이었습니다. 이 방식은 변경 범위가 작고 구현 비용이 낮다는 장점이 있었습니다.

하지만 리팩토링 문서를 정리하며 확인한 것은, 문제의 핵심이 단순히 loadMore 시점을 앞당기거나 늦추는 데 있지 않다는 점이었습니다. 기존 구조는 카드 높이가 모두 같다고 가정한 채 화면에 보여야 할 범위를 계산하고 있었기 때문에, 실제 높이가 달라질수록 스크롤 위치와 렌더링 결과 사이의 오차가 누적됐습니다. 또한 다음 데이터를 불러오는 기준도 ‘남은 항목 수’에 가까워, 사용자가 실제로 느끼는 목록 하단까지의 거리와 맞지 않았습니다. 게다가 높이 측정, 렌더 범위 계산, 상태 갱신이 한 흐름에 섞여 있어 원인을 분리해 분석하기도 어려웠습니다.

두 번째는 렌더링의 좌표 기준 자체를 실제 DOM 높이에 맞추는 방식이었습니다. 초기에는 예상 높이를 사용하되, 렌더된 카드의 실제 높이를 수집해 브라우저가 다시 그리는 타이밍에 맞춰 한 번에 반영하고, 이를 바탕으로 현재 화면에 보여야 할 범위와 목록 하단까지 남은 실제 스크롤 거리를 다시 계산하도록 바꿨습니다. 또한 데이터 로드 기준도 sentinel 노출 여부가 아니라, 사용자가 실제로 하단에 얼마나 가까워졌는지와 남은 항목 수를 함께 보도록 재정의했습니다.

이 방식은 구현 복잡도와 초기 비용이 더 컸지만, 사용자가 실제로 보는 구간과 로딩 시점을 더 직접적으로 맞출 수 있었습니다. 또한 측정, 계산, 스케줄링, 로드 정책을 분리해 이후에도 문제를 재현하고 수정할 수 있는 구조를 만들 수 있다는 점에서 더 적절하다고 판단했습니다.

결과적으로 구조 개선 이후 내부 측정 기준으로 Layout + UpdateLayoutTree 비용이 29.9% 감소했고, 16ms를 초과하는 장기 작업 발생 빈도도 58.1% 줄었습니다. 무엇보다 이전에는 설명하기 어려웠던 빈 구간, 늦은 렌더링, 중복 로드 문제를 테스트로 재현하고 수정할 수 있는 구조를 만들었습니다.

## 끝이 좋았던 경험과 좋지 못했던 경험을 각각 소개해주세요. 특히 좋지 못했던 경험에서 무엇을 느꼈으며, 이후 유사한 상황에서 어떻게 다르게 대처하고자 했는지(혹은 대처했는지) 서술해주세요.

끝이 좋았던 경험은 "Obsidian MCP Server를 개발해 npm에 배포했던 일" 입니다. 평소 Obsidian으로 지식을 정리하면서, AI가 제 로컬 문서를 더 잘 활용하고 흩어진 이미지·문서를 현재 작업 맥락에 맞게 정리해주면 좋겠다고 느꼈습니다. 그래서 Vault 문서 검색·열람, 컨텍스트 수집, frontmatter 제안·반영, 첨부파일 정리 기능을 포함한 MCP 도구를 직접 만들고 배포했습니다.

이 경험이 의미 있었던 이유는 단순히 기능을 구현했다는 점보다, 제가 만든 도구가 실제 사용자에게 사용되기 시작했다는 점이었습니다. 개발 인생 처음으로 제가 만든 도구가 배포 이후에도 실제 사용 맥락 안에서 소비되었고, 주간 다운로드 수가 300회를 넘는 결과를 보며 기술 자체보다 사용자의 불편을 먼저 정의하고, 그것을 실제로 쓸 수 있는 형태로 끝까지 완성하는 태도가 중요하다는 것을 배웠습니다. 이후에는 무언가를 만들 때도 “구현이 되었는가”보다 “실제로 문제를 해결하는가”를 먼저 기준으로 삼게 되었습니다.

반대로 끝이 좋지 못했던 경험은 "웹소켓 기반 실시간 베팅 서비스 프로젝트에서, 대기방 사용자가 방장이 투표를 시작한 직후 바로 참여하지 못하던 문제" 를 마주했을 때입니다. 처음에는 단순한 네트워크 지연으로 보였지만, 백엔드와 함께 양쪽 로그를 비교하며 원인을 좁혀 본 결과 대기방 진입 이후 소켓 연결, 방 참여, 실제 투표 가능 상태가 서로 다른 시점에 반영되는 구조적 문제에 가깝다는 점을 확인했습니다.

다만 프로젝트 마감이 며칠 남지 않은 상황에서 전체 흐름을 수정하는 것은 안정성 리스크가 크다고 판단했고, 팀과 논의 끝에 우선 사용자가 완전히 막히지 않도록 재시도 안내 UX를 적용해 피해를 줄이는 방향으로 대응했습니다. 당시에는 마감 직전의 현실적인 선택이었지만, 결과적으로 근본 해결은 아니었고 사용자 혼란도 남았습니다.

이 경험을 돌아보며 느낀 것은, 문제의 본질이 단순히 테스트 부족만은 아니라는 점이었습니다. 실시간 기능에서는 “연결되었다”, “방에 들어왔다”, “실제로 투표할 수 있다”처럼 비슷해 보이는 상태도 명확히 구분되어야 하고, 클라이언트와 서버가 어떤 이벤트를 기준으로 다음 상태로 넘어가는지에 대한 계약이 먼저 정리되어야 한다는 점을 배웠습니다. 당시에는 이런 준비 상태를 팀 차원에서 충분히 정의하지 못했고, 실제 사용자 시나리오 기준의 검증도 부족했습니다.

이후에는 기능이 논리적으로 동작한다고 가정하기보다, 핵심 사용자 시나리오와 상태 전이를 먼저 정의하고 이를 검증하는 방식으로 접근하려고 했습니다. 개인 블로그를 개발할 때도 이 교훈을 적용해, 포스트 링크 클릭 후 상세 페이지 제목이 안정적으로 렌더링되는지, 로딩 화면이 노출된 경우 정상적으로 사라지는지를 E2E 테스트로 검증했습니다. 이전에는 문제가 발생한 뒤 사용자 피해를 줄이는 방식으로 대응했다면, 이후에는 핵심 시나리오를 먼저 고정하고 이를 테스트와 개선의 기준으로 삼아 서비스의 안정성을 높이려는 방향으로 바뀌었습니다.
