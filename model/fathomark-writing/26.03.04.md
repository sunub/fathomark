## Layout Thrashing

**Layout(Reflow)** 은 브라우저가 요소의 기하학적 정보를 파악하는 곳입니다. 즉, 페이지에서의 크기와 위치를 확인하는 과정입니다. 이 과정은 브라우저가 수행하는 작업 중 연산 비용이 **가장 비싼** 작업입니다.

하나의 요소 크기가 변경이 되어도, 부모나 형제 요소들의 위치까지 연쇄적으로 다시 계산해야 하기 때문에 사용자 경험을 위해서는 **Layout 발생을 최소화**하는 것이 브라우저 렌더링 최적화의 핵심입니다.

### getBoundingClientRect

`getBoundingClientRect` 는 개발을 수행하다보면 이용하게 되는 DOM API 입니다. 이 API 가 제공하는 정보는 특정 DOM 요소의 top, left, right, height, width 와 같이 크기, 위치와 관련된 정보들을 모두 얻을 수 있기 때문에 굉장히 유용항 API 입니다.

하지만 이 API를 사용할 경우 반드시 알아야하는 사항이 있습니다. `getBoundingClientRect` 를 호출하면 **Layout 작업이 동기적으로 강제 실행**된다는 것입니다. 이 부분이 약간 의아할 수 있습니다. `getBoundingClientRect` 는 뷰표트를 기준으로 위치를 픽셀 단위로 반환하는 **읽기(Read)** 작업이지 DOM 요소를 조작하는 API가 아니기 때문입니다.

이걸 이해하기 위해서는 브라우저의 렌더링 큐 최적화와 Layout 이 이루어지는 조건에 대해서 이해해야합니다.

브라우저는 성능을 극대화하기 위해 JavaScript로 인한 DOM이나 CSS 변경 사항을 발생할때마다 매번 화면을 다시 그리는 것이 아닌, 변경 사항들을 렌더링 큐를 사용하여 다음 프레임에 Batching 하여 처리합니다.

이러한 처리과정 중에서 `getBoundingClientRect()` 를 호출하게 되면 브라우저가 가장 정확하고 최신 상태의 기하학 정보를 반환하기 위해서는 현재 큐에 쌓여서 아직 화면에 반영되지 않은 스타일이나 DOM 변경사항들을 먼저 전부 계산해야만 합니다.

즉, 이로 인해서 기존의 처리하기 위해 대기하고 있던 작업들은 무도 Flush 하고, 화면의 노드 배치를 게산하는 Layout 과정을 동기적으로 강제 실행하여 최신 DOM의 기하학 정보를 얻을 수 있게끔 강제됩니다.

```js
// 반복문 안에서 Write와 Read가 교차 발생하여 매번 Layout이 강제됨
for (let i = 0; i < elements.length; i++) {
  // Read (Layout 강제 실행)
  const rect = elements[i].getBoundingClientRect(); 
  // Write (렌더 큐에 변경 사항 추가)
  elements[i].style.width = rect.width + 10 + 'px'; 
}
```

만약 위와 같이 elements 내부의 모든 요소들에 대한 정보를 `getBoundingClientRect()` 를 통해서 정보를 Read 하게 된다면 elements의 크기만큼의 Layout 이 발생하기 때문에 Layout Thrashing 이 발생하게 됩니다.

> **Layout Thrashing 이란?**
>  JavaScript에서 요청/호출될 때 브라우저가 스타일과 레이아웃을 동기적으로 계산하도록 하는 것을 Layout Thrashing 이라고 합니다.

```js
// 1. Read 작업만 먼저 일괄 처리 (Layout 한 번만 발생)
const rects = elements.map(el => el.getBoundingClientRect());

// 2. Write 작업 일괄 처리
for (let i = 0; i < elements.length; i++) {
  elements[i].style.width = rects[i].width + 10 + 'px';
}
```

위의 코드에 대해서 자세히 이야기해보겠습니다. `rects` 의 배열을 구성하기 위해서 Layout 은 단 한번만 일어납니다. 한 번 이루어진 후에는 각 위치에 대한 정보를 `rects` 에 반영하면 되기 때문입니다.

`elements[i].style.width = ...` 와 같은 Write 코드가 JS 엔진에서 실행될 때, 브라우저는 그 즉시 화면을 Layout하지 않습니다. 대신 브라우저는 변경사항을 렌더링 큐에 쌓아둡니다.

Write 반복문이 모두 끝나고 현재 실행 중인 Call Stack 비면, 브라우저는 다음 화면 프레임을 그리기 위한 렌더링 파이프라인을 가동합니다. 바로 이때, 큐에 쌓여 있던 수많은 DOM 변경 사항들을 한꺼번에 반영하여 **단 한 번의 종합적인 Layout 연산**을 수행합니다.

위와 같은 최적화 과정에서 우리가 얻을 수 있는 것은 위와 같이 DOM의 **Read 작업과 Write 작업을 철저히 분리**하여 Batching하는 것이 중요하다는 것입니다. JS를 사용하여 DOM 요소를 조작하거나 기하학적인 정보를 읽어오는 과정은 필연적으로 **Layout** 작업을 동반합니다. 그렇기 때문에  앞서 설명한 `getBoundingClientRect` 이외에도`offsetHeight` 등 [주의해야하는 많은 속성](https://gist.github.com/paulirish/5d52fb081b3570c81e3a) 들이 존재하니 한 번 확인해보시는 것도 좋을 것 같습니다.
