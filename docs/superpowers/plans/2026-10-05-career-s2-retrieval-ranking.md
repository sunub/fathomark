# S2: 검색 순위와 "근거 없음" 보고

**목표**: 경험 노트를 의견·스터디 노트보다 우선하고, 근거가 부족하면 모델이 채우지 않도록 `supported: false`를 돌려준다.

**상태**: **합격** (2026-10-08, 새 판정용 셋 60개에서 네 지표 모두 통과). 2026-10-06 판정용에서는 미달이었고, 이후 문항 머리말 청크 제외와 Gemma 근거 판정을 더했다. 결과와 한계는 [측정 문서](../../testing/career-retrieval-baseline.md)의 "새 판정용 측정 결과"에 있다.

**선행**: S1(기준선). **프레임워크**: 없음. 의도적으로 임베딩을 넣지 않는다(ROADMAP Phase 3: lexical이 합의된 목표를 못 넘을 때만 도입).

## 범위

- 점수 방식을 IDF 가중과 MSM 필터로 바꾼다. 여러 노트에 나오는 흔한 단어(질문 상투어 "경험", "서비스" 등)는 점수가 낮아지고, 질문 단어가 일정 개수 이상 맞은 노트만 후보가 된다.
  - IDF: 단어가 나오는 노트가 적을수록 높은 가중치(`ln(전체 노트 수 / 단어가 나온 노트 수) + 1`).
  - MSM: 질문 단어 1~2개면 1개, 3~4개면 2개, 5개 이상이면 절반 이상 맞아야 후보가 된다. (obsidian-mcp-server의 `Indexer.search`와 같은 규칙. 이 값이 한국어 질문에 맞는지는 평가로 확인한다.)
- 노트 종류 판별: frontmatter `type`, 태그, 폴더 규칙 중 사용자 설정으로 "경험 노트"를 지정할 수 있게 한다. 기본 규칙은 frontmatter `type`이다.
- 점수에 종류 가중치와 제목·헤딩 가중치를 더한다.
- 질문 단어의 조사를 처리한다(규칙 기반, 짧은 어근은 보호).
- 결과에 `supported` 판정과 이유(`no_match`, `below_threshold`)를 추가한다.
- 평가 절차를 보강한다(아래 "평가 절차").

범위 밖: 임베딩·재순위, 청킹(`@langchain/textsplitters`), 영속 역색인, UI, 문단 단위 채점(S3).

## 평가 절차

obsidian-mcp-server의 `docs/search-quality-evaluation.md`에서 가져온 원칙이다. S1 고정셋은 12개이고 기준선 문제를 관찰한 질문들이라, 이 셋만으로 임계값을 맞추면 과적합한다.

1. **보류(held-out) 질문을 먼저 쓴다.** 구현 전에, 현재 검색 결과를 보지 않고 질문 약 10개와 정답 노트를 `plugin/tests/fixtures/career-cases-heldout.json`에 쓴다(답이 있는 질문과 근거 없는 질문 모두). 이 셋은 임계값과 가중치를 정하는 데 쓰지 않고, 마지막에 한 번 측정한다.
2. **질문 유형 태그.** 모든 질문에 `type`을 붙인다: `exact_title`, `keyword`, `semantic`, `multi_doc`, `no_answer`. 유형별 수치를 따로 기록한다.
3. **단계별 비교.** 아래 구성마다 같은 고정셋으로 수치를 기록한다. 어떤 변경이 올렸고 어떤 변경이 해로웠는지 분리하기 위해서다.
   - A. 기준선(현재)
   - B. A + IDF + MSM
   - C. B + 종류 가중·제목/헤딩 가중
   - D. C + 조사 처리
   - E. D + `supported` 임계값(최종)
4. **질문별 개선/악화 건수.** 구성 간 평균만이 아니라 "개선 N개, 악화 N개, 동일 N개"를 적는다. 표본이 작아서 평균보다 이쪽이 정직하다.
5. 수치는 방향 확인용이라고 문서에 명시한다. 신뢰구간은 계산하지 않는다(표본 부족).

## 인터페이스

- Produces: `searchVault(...)`가 `{ references, omitted, supported: boolean, reason?: "no_match" | "below_threshold" }`를 반환. S4의 retrieve 단계가 `supported`를 읽는다. 이 반환 형식은 나중에 `RetrievalBackend` 인터페이스(아래 "결정 게이트")의 계약이 된다.
- Consumes: S1의 `recallAtK`, `reciprocalRank`, `abstentionRate`, 고정셋.
- `supported` 임계값은 절대 점수가 아니라 "질문 단어의 IDF 합 대비 최고 점수 노트가 맞춘 IDF 합의 비율"로 정한다(노트 수가 달라져도 덜 흔들리게 하려는 설계 가정이다. 실제로 그런지는 평가로 확인하고, 아니면 다른 방식으로 바꾼다).
- IDF에 필요한 문서 빈도는 `searchVault`가 노트를 읽는 같은 패스에서 센다(질문 단어별 포함 노트 수를 모은 뒤 점수를 계산하는 2단계). 영속 색인을 만들지 않으므로 `onload`는 가볍게 유지된다.

## 완료 기준

- 고정셋에서 recall@3이 기준선(0.44)보다 개선되고, 의견 노트가 경험 노트보다 상위에 오지 않는다.
- 근거 없는 질문은 `supported: false`다.
- 보류 질문 셋에서도 기준선보다 나아졌는지 별도로 기록한다. 고정셋에서만 좋고 보류 셋에서 나빠졌다면 과적합으로 보고 결과를 그대로 적는다.
- 개선이 목표에 못 미치면 그 수치와 함께 임베딩 도입 필요 여부를 문서에 적는다(이 슬라이스에서 구현하지 않는다).

## 합격선 (2026-10-06 확정)

위 "완료 기준"은 이 슬라이스가 기준선보다 나아졌는지 보는 것이고, 합격선은 검색이 제품에서 쓸 만한지 보는 기준이다. ROADMAP Phase 3의 "합의된 목표"가 이것이며, 아래 네 가지를 **모두** 만족해야 합격이다. 하나라도 못 미치면 아래 "결정 게이트"의 검토 대상이 된다.

| # | 지표 | 합격선 | 정의 |
|---|---|---|---|
| 1 | recall@3 | **0.75 이상** | 답이 있는 질문 중 정답 노트가 상위 3개 안에 든 비율. 실제 Vault 평가셋은 같은 경험이 자기소개서, 이력서, 포트폴리오에 중복돼 있어 정답 노트 중 **하나라도** 상위 3개에 들면 적중(any-hit)으로 센다. 합성셋은 기존대로 찾은 비율의 평균 |
| 2 | 근거 없음 차단률 | **0.90 이상** | 근거가 없어야 하는 질문 중 `supported: false`로 응답한 비율 |
| 3 | 오차단률 | **0.20 이하** | 답이 있는 질문 중 `supported: false`로 응답한 비율 |
| 4 | 비경험 노트 1위 비율 | **0.10 이하** | 답이 있고 결과가 하나 이상인 질문 중 1위 노트가 경험 노트가 아닌(의견·스터디 등) 비율 |

**근거:** 제품 흐름이 "검색 → 사용자가 근거 선택"이라 1위 정확도보다 상위 3개 안에 정답이 있는지가 중요하다. 5개 중 4개 가까이 맞아야(0.75) 뒤 단계가 틀린 근거 위에서 돌아가는 일이 드물다. 2번과 3번은 서로의 부작용을 막는다(다 막아서 2번을 채우면 3번이 깨진다). 4번은 ADR 0007이 지적한 "의견 글이 경험 노트보다 먼저 잡힌다"를 직접 잰다.

**이 숫자는 합성 고정셋으로 판정하지 않는다.** 합격 판정에는 실제 노트와 실제 지원 질문으로 만든 평가셋이 필요하다.

- 답이 있는 질문 20개 이상(한 질문이 0.05씩 움직인다), 근거가 없어야 하는 질문 5개 이상.
- 4번을 재려면 평가 노트마다 종류(경험, 의견, 스터디 등) 라벨이 필요하다.
- 개인 정보가 든 평가셋은 저장소에 커밋하지 않는다. 숫자와 질문 유형별 요약만 `docs/testing/`에 기록한다.
- 합성 고정셋과 보류셋의 수치는 방향 확인용으로만 쓰고 합격 여부를 말하지 않는다.

## 결정 게이트: 의미 검색 (이 슬라이스에서 구현하지 않음)

측정 결과를 기록한 뒤, 위 합격선에 못 미치고 부족분이 단어가 달라서 생기는 것일 때만 검토한다. ADR 0002는 별도 프로세스를 "측정된 한계" 전에는 금하고, ADR 0007은 사용자에게 Python이 필요 없다고 정했다.

### 근거 1: 실패 진단 (2026-10-06, 고정셋에서 답이 있는 9개)

| 원인 | 질문 | 개수 |
|---|---|---|
| 찾음 | incident, data, automation | 3 |
| 맞는 노트와 겹친 단어가 1개뿐인데 MSM이 2개를 요구해 탈락 | perf, latency, ci, search | 4 |
| 겹친 단어 0개(어휘 불일치) | lead, conflict | 2 |

6개 실패 모두 "맞는 노트와 글자가 거의 안 겹친다"는 점에서 의미 기반 매칭이 도움이 될 수 있다. 다만 4개는 MSM 규칙이 직접 원인이라 규칙 조정으로 일부 회복될 수 있다. 표본은 합성 데이터 9개다.

### 근거 2: 참고 구현 (`obsidian-mcp-server`, `VaultManager.hybridSearch`)

| 단계 | 내용 |
|---|---|
| 청킹 | 500자(겹침 50), 헤딩 1~3단계를 청크 앞에 붙임 |
| 임베딩 | `paraphrase-multilingual-MiniLM-L12-v2`, 서버 프로세스에서 transformers.js 실행 |
| 저장 | LanceDB(`.obsidian/vector_cache`), 백그라운드 증분 색인 |
| 검색 | 키워드(IDF+MSM, 문서 단위)와 벡터(청크 단위)를 병렬로 돌려 RRF(K=60)로 합침 |
| 재정렬 | 의미 거리 0.2 미만이 있으면 생략, 아니면 `bge-reranker-base`. 모델이 없으면 키워드로 폴백 |

**핵심 차이:** 그 프로젝트의 MSM은 키워드 갈래에만 걸리고, 단어가 안 겹치는 문서는 벡터 갈래가 살린다. S2는 MSM을 단독 검색기에 적용했으므로 어휘가 다르면 후보에서 사라진다. 의미 검색 없이 MSM만 쓰는 구성은 참고 구현의 설계가 아니다.

### 목표 구조 (임베더를 도입하는 경우)

- 키워드(IDF+MSM)와 청크 임베딩을 RRF로 합친다. 임베딩을 쓸 수 없으면 지금의 키워드 검색으로 내려간다.
- 둘 다 `RetrievalBackend` 인터페이스 뒤의 구현으로 둔다. 반환 형식(`supported` 포함)은 위 "인터페이스"의 `searchVault`가 계약이다.
- 근거 단위는 청크다. 지금의 "첫 일치 문단" 발췌보다 S3(주장별 근거 검증)의 요구와 맞는다.
- 벡터 저장은 플러그인 데이터 폴더의 단순 파일과 수정 시간 기준 증분 갱신으로 시작한다. 노트 수백 개 규모면 충분하다는 것은 추정이고 측정이 필요하다. LanceDB 같은 네이티브 모듈은 번들 조건(S0)과 맞지 않을 수 있어 사용 전에 확인한다.
- 리랭커는 보류한다. 효과를 보여 주는 자료가 없다.
- 의견 노트가 근거로 인정되는 문제는 임베딩으로 풀리지 않는다(의견 노트가 의미상 가장 가까울 수 있다). 노트 종류 판별은 별도로 해결한다.

### 검토 순서

0. **선행:** 합격선과 실제 노트·질문으로 만든 평가셋(답이 있는 질문 20개 이상). 이 둘 없이는 아래 어느 것도 판정할 수 없다.
1. 키워드 단독에서 MSM 완화 효과 측정. 임베더 없이 가능한 가장 싼 기준선이다.
2. Ollama 임베딩 + 키워드 하이브리드. 이 제품은 Gemma 4 때문에 이미 Ollama가 필요해서 새 실행 환경이 늘지 않고 번들도 그대로다. 로컬 loopback이라 외부 전송이 아니다.
3. 플러그인 안 transformers.js. 커뮤니티 스토어에 선례가 있으나(Smart Connections) 번들 크기와 Obsidian 안 동작은 확인이 필요하다.
4. Python 추론 서버. 위가 품질이나 리소스에서 막혔을 때만 검토한다.

### 도입 조건

- 같은 평가셋(고정셋과 보류셋)에서 키워드 검색을 이겨야 한다. 의미 유형의 recall이 오르고 다른 유형이 떨어지지 않아야 한다.
- 첫 색인 시간과 질문당 지연의 상한을 도입 전에 정한다. 값은 평가셋을 확정할 때 함께 정한다.
- 한국어 질문으로 평가해 모델을 고른다. 영어 중심 모델은 한국어 품질이 검증되기 전에는 기본값으로 쓰지 않는다.
- Python 서버를 도입한다면 다음을 모두 지킨다. 새 ADR로 ADR 0001·0002·0007을 보정한다. 사용자가 직접 설치하는 선택 구성요소이고 꺼져 있으면 TS 검색으로 내려간다. `127.0.0.1`에만 바인딩하고 공유 비밀 헤더를 요구한다. 같은 평가셋에서 위 단계들을 이긴다.

### 커뮤니티 스토어 배포 제약 (Obsidian 공식 문서 기준, 2026-10-06 확인)

- 번들 크기 규칙은 Plugin guidelines, Developer policies, Submission requirements 어디에도 없다. 900 KB는 `plugin/build.mjs`의 자체 경보선이며 의도적으로 올릴 수 있다.
- 플러그인은 자기 자신이나 의존성을 설치·업데이트할 수 없다. 클라이언트 텔레메트리는 금지다. 외부 서비스를 쓰면 무엇을 왜 쓰는지 밝혀야 한다. Node/Electron API를 쓰면 `isDesktopOnly: true`여야 한다(이미 해당).
- 따라서 Python 서버나 모델을 플러그인이 알아서 받아 설치하는 구조는 마찰이 크다. 정책이 서버를 명시적으로 금지하는지는 확인하지 못했다.

### 검증되지 않은 것

- 임베딩 모델의 한국어 품질. Ollama가 쓸 만한 다국어 임베딩 모델을 제공하는지.
- LanceDB를 플러그인 번들에 넣을 수 있는지.
- 참고 구현이 `search_query:`/`search_document:` 접두어를 붙이는데 이는 nomic·e5 계열의 관례이고 사용한 MiniLM 계열에는 필요 없어 보인다. 모델과 프롬프트가 맞는지 직접 확인하지 않았다.
- 이 문서의 이전 판에 있던 "노트 391개 색인에 11분"과 "리랭커가 MRR을 0.672에서 0.579로 낮춤"은 인용한 `docs/search-quality-evaluation.md`가 저장소와 그 프로젝트의 git 기록(384개 커밋)에 없어 삭제했다.

## 한계

- 평가는 문서 단위다. 그러나 `searchVault`는 질문 단어가 든 첫 문단을 발췌로 돌려준다(`vault-search.ts`의 `paragraphs(...).find(...)`). 문서가 맞아도 발췌 문단이 틀릴 수 있고, 이 슬라이스의 지표는 그것을 잡지 못한다. 문단 단위 채점은 S3(주장별 근거 검증)에서 한다.
- 표본이 작고 합성 데이터라 수치는 방향용이다.

## 리뷰 초점

- 임계값이 합성 데이터에 과적합되지 않았는가. 보류 셋 결과가 고정셋과 같은 방향인가.
- 설정이 비어 있을 때(경험 노트 지정 없음) 종류 가중치를 적용하지 않고 기존 동작이 유지되는가.
- MSM과 IDF가 질문이 매우 짧을 때(단어 1~2개) 지나치게 많이 걸러내거나 아무것도 걸러내지 못하지 않는가.
- 조사 제거가 `가`, `이`로 끝나는 명사를 잘못 자르지 않는가.
