공통 도구 인터페이스와 도구별 개선 요구사항

상태: 설계 제안 · 제품 코드 변경 전
검토 기준일: 2026-10-11

이 문서는 도구를 추가할 때 지켜야 할 공통 정의, 실행 경계, 상태 전이와 도구별 개선 요구사항을 정한다. 개별 도구의 기능·요구사항·워크플로우·시각화는 아래 연결된 문서에서 관리한다. 이 README의 공통 경계는 기존 문서에 부족했던 사항을 보완하며, 대기·재개와 새 도구의 구현 완료를 뜻하지 않는다.

현재 Registry는 이미 도구를 교체하고 추가할 수 있는 추상화를 갖추고 있다. 유지할 기반은 ToolDefinition과 검사된 실행 경로이며, 먼저 보완할 부분은 결과 상태·사용자 입력 대기·단계별 허용 도구·실행 문맥이다.

💡 추상화: 호출하는 쪽이 실제 구현의 세부 사항 대신 공통된 약속으로 기능을 사용하는 것이다. 여기서는 도구 이름·입력·결과를 사용하고 Vault나 네트워크 접근 방식은 도구 구현에 맡긴다.

1. 두뇌·손·세션의 분리를 어떻게 적용할 것인가

Anthropic은 모델과 Harness, 도구 실행 환경, 세션 로그를 독립적으로 교체·복구할 수 있도록 분리했다. Fathomark에는 이 책임 분리 원칙을 적용한다. 분산 서비스의 컨테이너 재생성이나 영구 세션 복구는 이번 단계의 요구사항으로 가져오지 않는다. Anthropic 공식 설계

💡 Harness: 모델 호출, 다음 단계, 권한·한도, 대기와 취소를 관리하는 실행 코드다. 실행 환경은 도구가 실제 작업을 수행하는 대상이며 현재는 주로 Obsidian의 Vault와 허용된 공개 자료다.

책임 Fathomark에서 담당할 일 담당하지 않을 일
두뇌: 모델과 Harness 행동 제안과 검사, 다음 단계, 예산, 질문·승인 대기, 결과 해석 도구 내부의 파일·HTTP 처리 방법
손: 도구 구현과 주입된 서비스 정해진 입력으로 필요한 자료를 조회하거나 변경안을 생성하고 결과를 반환 전체 실행 종료, 무제한 재시도, 사용자 승인 생성
세션: 실행 기록과 재개 상태 호출·결과·질문·답변·승인·취소를 식별자로 연결 모델의 문맥 자체를 영구 원본 기록으로 취급

현재 RunSession은 UI 스냅샷과 완료 대화를 메모리에 보관한다. 새 실행에서 이벤트 목록을 초기화하고 텍스트 이벤트를 합치므로, 장애 뒤 동일 작업을 복구하는 영구 이벤트 로그와는 다르다. 초기 버전은 작업 중 대기·재개에 필요한 상태만 확장하고 앱 재시작 복구는 별도 설계한다.

같은 프로세스 안에서도 인터페이스와 상태 소유권을 분리할 수 있다. 하지만 같은 프로세스가 종료되면 모두 영향을 받을 수 있으므로, 인터페이스만으로 장애 격리나 영구 복구를 보장하지 않는다. 현재의 플러그인 내부 Harness 결정은 유지한다.

2. 현재 registry.ts의 추상화 수준

ToolDefinition과 ToolRegistry는 도구의 공통 정의와 등록·조회 역할을 이미 제공한다. Vault 접근은 등록 시 VaultReader로, Wikipedia의 네트워크 호출은 fetch로 주입된다. 실제 작업을 교체하는 접점이 이미 run(input, context)에 있다.

현재 구성 현재 역할 판단
name, description, parameters 모델에게 공개하는 이름·설명·입력 형식 유지. 모델이 도구를 선택할 정보가 필요함
input, output 실제 입력과 반환값 검증 유지. 문자열 인터페이스만으로 대체하지 않음
capability, approval 제품 권한 검사에 쓰는 선언 유지하되 권한 부여는 Harness에서 수행
timeoutMs, resultBudgetTokens 실행 시간 제한과 결과 예산 선언 유지. 시간 제한은 실행기에서 검사하지만 결과별 토큰 예산은 현재 선언만 있고 강제 경로가 없음
provenance 반환 결과에서 출처 추출 유지. 도구별 결과 형식에 맞춰 추출하고 출처가 없는 결과도 허용
run(input, context) 등록된 도구의 실제 작업 기존 서비스를 주입하는 방식 유지
register, get, definitions, names 중복 이름 차단과 등록 목록 관리 등록·조회에 집중. 재시도나 세션 복구를 Registry에 넣지 않음

💡 입출력 형식 검증: 전달한 값이 도구가 받기로 정한 형태와 일치하는지 검사하는 것이다. 출처 기록은 반환한 정보가 어떤 노트·자료·사용자 답변에서 왔는지 추적하는 정보다.

executeTool은 이름 조회, 권한·승인, 입력, 시간 제한, 반환값을 검사한 뒤 모델용 문자열과 출처를 반환한다. 따라서 공통 실행 진입점도 이미 존재한다. [Registry → 새 Backend → run]처럼 동일한 위임을 반복하는 새 계층은 지금 추가하지 않는다.

현재 resultBudgetTokens는 도구 정의에 선언돼 있지만 실행 경로에서 실제 소비량을 검사하거나 제한하는 데 사용되지 않는다. 전체 모델 요청의 문맥 예산 검사는 개별 도구 결과 예산과 다르다. 후속 구현에서는 결과를 모델 이력에 넣기 전에 예산을 확인하고, 초과 시 도구별 부분 결과 또는 명시적 오류로 처리해야 한다. JSON 문자열이나 원문 구절을 임의로 잘라 반환 형식과 출처를 훼손하지 않는다.

3. 보완해야 할 네 가지 경계

3.1 등록된 도구와 현재 허용된 도구

현재 Agent Loop는 offeredTools로 등록된 도구 중 현재 단계(explore·revise)와 권한 정책(사용자 설정 포함)이 허용한 정의만 모델에 전달하고, 실행 직전에도 같은 단계·권한 검사를 한다. 자료 범위에 따른 제한은 아직 없다. 등록된 도구는 설치된 기능 목록이며, 지금 단계에서 사용할 수 있는 기능 목록과는 다르다.

Harness가 현재 단계·사용자 설정·자료 범위에 맞는 정의만 모델에 공개하고, 호출 실행 직전에도 같은 허용 목록을 검사한다. 숨긴 도구 이름을 모델이 직접 요청해도 실행되지 않아야 한다. 탐색 단계에서 propose_revision이나 실제 에디터 적용을 허용하지 않는다.

3.2 공통 실행 문맥과 도구별 서비스

현재 ToolExecutionContext에는 공통 취소 신호 외에도 researchTopic, allowedWikipediaPages, Wikipedia 전용 onResearchQuery가 있다. 새 도구마다 이 공통 문맥에 관련 없는 필드를 더하면 도구들이 서로의 상태에 결합된다.

공통 문맥은 취소 신호, 실행·호출 식별자, 필요한 좁은 상태 접근에 집중한다. 실행·호출 ID와 자료 범위는 모델 입력을 신뢰해 받지 않고 Harness가 지정한다. Vault 조회·공개 자료 읽기·작업 상태 보존은 필요한 도구에만 제한된 서비스로 주입한다. Wikipedia 주제와 허용 페이지 상태도 해당 도구에만 전달한다.

큰 App 객체, 전체 Registry, 모든 권한을 바꾸는 객체를 모든 도구에 제공하지 않는다. 현재 Registry와 Loop에 권한 형식이 연결돼 있으므로 이 부분은 후속 구현에서 의존 방향을 확인하며 좁게 분리한다.

3.3 내부 결과와 모델용 문자열

execute(name, input) 형태의 호출은 유용하지만 반환값을 내부에서도 문자열 하나로 통일하면 대기·누락·오류·근거 상태를 다시 문자열에서 추측해야 한다. 내부에는 검증된 결과와 출처를 유지하고 모델에 전달하는 마지막 단계에서 문자열을 만든다.

공통 실행 결과가 구분할 상태는 다음과 같다. 이는 목표 계약이며 현재 코드에 구현된 타입이 아니다.

실행 결과 Harness가 할 일 모델에 전달할 때
완료 검증된 결과와 출처를 기록 현재처럼 연결된 호출 ID의 결과를 한 번 전달
사용자 입력 필요 질문·호출 ID와 재개 상태를 보관하고 실행 대기 답변을 얻은 뒤 해당 호출의 완료 결과를 전달
실행 실패 오류 종류와 남은 한도로 중단·복구 가능성을 판단 빈 검색 결과 대신 오류를 구분해 전달

완료 결과 내부의 일부 생략, 검색 결과 없음, 대상 없음 등은 도구별 형식으로 유지한다. 모든 도구에 동일한 references·omitted 배열을 강제하지 않는다. 필요한 출처는 기존 provenance 같은 추출 접점으로 통일한다. ask_user의 답변 출처에는 질문·답변 식별자가 필요하므로 현재의 Vault·Wikipedia 출처 타입을 확장해야 한다.

3.4 짧은 도구 실행과 긴 사람 입력 대기

현재 run은 시간 제한 안에 끝나는 Promise이고, 승인 필요한 실행은 approval_required 오류로 거부된다. 상태 이름과 이벤트가 있다는 것만으로 실제 승인 대기·재개가 연결된 것은 아니다.

ask_user는 사용자 답변까지 run 안에서 기다리지 않는다. 질문 요청을 만들어 짧은 실행으로 반환하고 Harness가 입력 대기 상태를 소유한다. 답변을 받으면 실행·질문·호출 ID를 검사해 결과를 완성한다. 대기 중 모델 호출·도구 호출·활성 실행 타이머를 멈추며, 재개해도 누적 한도는 유지한다.

일반 완료 결과를 내는 기존 run은 작은 어댑터로 공통 완료 결과에 연결할 수 있다. 대기 기능을 추가할 때는 일반 도구 반환값을 단순히 unknown으로 넓혀 구분하지 말고, 실행 종류와 검증할 완료 결과의 관계를 명시해야 한다. 정확한 타입 형태는 구현 단계에서 계약 테스트와 함께 정한다.

4. 권장하는 공통 호출 흐름

모델: 도구 이름과 입력을 제안
  ↓
Harness: 실행·호출 ID, 단계별 허용 목록, 권한·한도 확인
  ↓
공통 실행 진입점: 입력 검증·취소·짧은 실행 시간 제한
  ↓
도구 run: 주입된 Vault·자료 읽기·질문 요청 기능 사용
  ↓
반환값 검증: 형식 있는 결과·출처·누락·오류 유지
  ↓
Harness: 완료 / 사용자 입력 대기 / 실행 실패 분기
  ↓
세션 상태·이벤트 기록 → 모델에 필요한 관측 전달

Registry는 도구 정의와 등록된 구현을 제공하고, 실행 진입점은 검사와 호출을 맡으며, Harness는 다음 단계와 대기·재개를 관리한다. 세션 기록의 저장 방식은 이 셋의 내부 작업과 분리한다.

권한과 승인 완료 여부는 모델이 입력으로 선언할 수 없다. 실제 승인 경로가 필요할 때는 Harness의 신뢰된 상태로 검사한다. propose_revision은 변경안만 반환하므로 실제 적용 승인을 기다리는 도구로 만들지 않는다.

공통 호출의 목표 형태를 다음처럼 표현할 수 있다. 아래는 동작 계약을 설명하는 표기이며 현재 타입 선언이나 구현 코드는 아니다.

execute({ name, input }, trustedContext)
  → completed({ output, references, modelContent })
  | waiting_for_user({ request })
  | failed({ code, message })

name·input은 모델의 제안이며, trustedContext의 실행·호출 ID, 현재 단계, 취소 신호와 자료 권한은 Harness가 제공한다. output은 도구별 형식으로 검증된 원본 결과, references는 해당 결과의 출처, modelContent는 모델에 전달할 표현이다. request는 질문 내용과 필요한 사실의 요청이며, 질문 ID와 재개 상태는 Harness가 부여·보관한다. 실패의 복구 여부는 도구가 반환한 문장을 따르지 않고 오류 종류와 제품 정책으로 결정한다.

도구별 run은 해당 도구의 입력과 필요한 서비스만 알고, 전체 대화·모든 도구·세션 저장 구현을 알지 않도록 한다. 검사된 실행 진입점은 이 개별 반환을 공통 실행 결과로 정리한다. 이 구조가 원격 실행 어댑터 없이도 현재 적용할 수 있는 최소 공통 인터페이스다.

5. 실패·재시도·중복 호출 요구사항

현재 도구 호출 처리는 결과를 content·empty·error 관측으로 구분한다. 잘못된 입력은 한 번 수정할 기회를 주고, 권한 거부는 결과로 돌려주며, 시간 초과는 한 번 재시도한다. 그 밖의 실행 오류는 전체 실행을 종료한다. empty는 증거 도구가 근거를 인용하지 못한 경우이며 아직 소비하는 곳이 없다. 형식 오류·네트워크 실패의 복구 방식은 정해지지 않았다.

  • 결과 없음은 정상 완료의 한 종류이며, 네트워크 실패·형식 오류·시간 초과와 구분한다.
  • 도구는 전체 작업의 재시도와 종료를 스스로 결정하지 않는다. 읽기 재시도도 Harness의 남은 한도와 정책을 따른다.
  • 모든 오류를 재시도하지 않는다. 권한 거부·잘못된 입력·읽기 오류의 복구 방식은 각각 다르다.
  • 동일한 호출 ID가 재전달됐을 때 결과 재사용과 실제 재실행을 구분한다. 현재는 호출 수 증가가 중복 결과 확인보다 먼저이므로, 후속 구현에서 한도를 어떤 시점에 소비하는지 명시한다.
  • 취소 후 도착한 작업 결과·사용자 답변은 반영하지 않는다.
  • 변경을 발생시키는 작업을 재실행할 때는 동일 승인으로 두 번 적용되지 않아야 한다. 이 책임은 기존 승인·적용 경로에 유지한다.

초기 버전은 메모리 안의 상태와 대기·재개를 지원한다. 프로세스 장애 뒤 복구하려면 상태를 외부에 보존하는 계약이 추가로 필요하며, 현재 RunSession만으로 이를 보장하지 않는다.

6. 기존 네 도구의 개선 방향

현재 앱 진입점은 빈 Registry와 가짜 모델을 사용한다. 아래 도구는 구현된 모듈이지 설치된 앱에서 완성된 커리어 실행 경로로 연결된 상태가 아니다.

도구·문서 유지할 부분 보완할 부분
search_vault 실제 입력 query·limit, 경험 우선 검색, 선택적 의미 검색, 구절·경로 출처 내부 supported·reason을 출력 형식에 선언해야 검사 후에도 유지됨. 작성 가능성의 참고값이며 사실 검증 통과가 아님
read_note 실제 입력 path·선택적 heading, 경로 검증, VaultReader 주입 대상 없음·제목 없음·구절 없음·일부 생략을 구분하고 반환값만으로 식별 가능하게 함
search_wikipedia 실제 입력 topicId, 사용자 공개 주제만 전송, 허용 페이지 등록 Wikipedia 전용 상태를 좁은 실행 서비스로 전달. 후보 요약과 실제 본문 근거 구분 유지
read_wikipedia_page 실제 입력 pageId·language, 이번 검색의 허용 페이지 제한 원문 추출 없음과 네트워크 실패를 구분. 읽기 재시도 여부와 한도는 Harness에서 관리

search_vault의 내부 판정이 사라지는 이유는 현재 출력 형식에 해당 필드가 없고, 실행 진입점이 검증된 결과만 직렬화하기 때문이다. 설명문이나 프롬프트를 추가하는 것으로 해결할 문제가 아니다.

7. 새 여섯 도구에 필요한 실행 계약

도구·문서 실행 형태와 요구사항 구현 방향
ask_user 짧은 질문 요청 생성 → Harness 대기 → 답변으로 해당 호출 완료 대기 결과·질문/답변 ID·재개 상태가 먼저 필요. 사용자 답변 출처를 노트와 구분
get_note_context 허용된 노트의 제목·연결 후보를 즉시 반환 좁은 Vault 조회 서비스 주입. 후보 수·깊이 제한. 연결을 사실 근거로 자동 등록하지 않음
read_public_source 허용된 본문 또는 공개 자료 주소를 읽어 결과 반환 붙여넣기부터 지원. 외부 읽기에는 자료 허용·전송 동의·주소/리디렉션/응답 크기 검사 필요
search_public_sources 검증된 공개 조사 주제로 후보 반환 입력 주제와 외부 전송 검사 유지. 현재 general_web 거부 정책을 의도적으로 확장하는 별도 작업 필요
save_working_note 요청 범위의 근거표·개요·남은 질문 보존 우선 Harness/세션 상태로 처리. 모델이 선택적으로 저장해야 하는 요구가 확인될 때만 도구로 등록
propose_revision 대상 버전·유지 사실·기준 → 변경안 반환 공통 모델 호출과 검증을 재사용. 도구는 실제 쓰기 권한을 갖지 않고 승인·적용은 밖에서 수행

외부 읽기와 검색은 현재 권한 표에서 허용된 기능이 아니다. 새 도구를 Registry에 등록하는 것만으로 활성화하지 않으며, 해당 기능에 필요한 권한을 명시적으로 정의하고 검사해야 한다. Wikipedia 설정 하나를 일반 웹 접근 권한으로 재사용하지 않는다.

작업 메모 저장도 의미를 고정한다. 이 문서에서 의미하는 것은 요청 범위의 상태 보존이며 사용자 Vault 파일 생성이 아니다. Vault 노트 쓰기를 원한다면 별도 기능·승인·대상 검사로 설계한다.

도구 정의에 이 표의 항목을 모두 새 필드로 추가한다는 뜻은 아니다. 정의에 둘 정보, 실행 정책에 둘 규칙, 세션 상태에 둘 식별자를 구분한다. 새로운 도구마다 임의의 실행 경로를 만들기보다 기존 검사 경로와 입력·출력 검증을 재사용한다.

9. 가장 작은 보완 순서

  1. 기존 결과 계약 보완: 검색의 판정 필드 보존, 대상 없음·빈 결과·부분 결과·오류 구분부터 검증한다. 선언된 개별 결과 예산의 검사·초과 처리도 연결한다.
  2. 단계별 허용 도구: 모델에게 제공할 정의와 실제 호출 시 검사할 허용 목록을 일치시킨다.
  3. 공통 문맥 정리: 취소·실행 식별자와 Wikipedia 전용 상태를 구분하고 필요한 서비스만 주입한다.
  4. 사용자 입력 대기: 기존 완료 경로를 유지하며 대기 결과·질문 상태·재개·취소를 추가한다. 질문 대기에 도구 타임아웃을 계속 적용하지 않는다.
  5. 새 읽기 도구와 수정 제안: 공통 검사 경로에 연결한다. 외부 자료와 사용자 답변의 출처 확장, 외부 권한 계약을 함께 처리한다.
  6. 작업 상태 저장 요구 확인: 기존 실행 상태로 부족한 경우에만 선택적 도구나 영속 저장을 추가한다.

Registry 자체는 유지한다. 단계별 조회가 필요하면 얇은 목록 필터나 조회 기능을 추가할 수 있지만, 실행 정책·대기·세션 복구를 Registry 메서드로 모으지 않는다. parameters와 실제 입력 검사 형식의 중복도 현재 계약 테스트를 유지하고, 자동 생성은 실제 불일치 비용이 확인될 때 검토한다.

10. 이번 단계에서 채택하지 않는 확장

독립 컨테이너 생성·provision, 분산 세션 저장소, 모든 도구에 대한 범용 자동 재시도, Registry와 run 사이의 중복 실행 Backend는 추가하지 않는다. 원격 MCP·CLI 등 서로 다른 실행 방식이 실제 필요해지면 해당 도구의 좁은 실행 어댑터부터 도입한다.

💡 어댑터: 서로 다른 실제 구현을 제품이 사용하는 공통 호출 방식에 맞추는 연결 코드다. 현재 VaultReader와 주입된 fetch도 구현을 교체하는 접점이다.

인터페이스 분리는 구체 도구의 구현과 전체 작업의 상태 관리를 분리하기 위한 것이다. 프로세스 위치·저장 방식·실행 환경의 복구 기능은 실제 요구에 따라 별도로 결정한다.

11. 검증 기준과 관련 문서

후속 코드 변경에서는 기존 도구의 정상 반환과 취소·권한·시간 제한 동작을 유지해야 한다. 반환한 검색 판정 필드가 모델 문자열과 Harness의 내부 결과 모두에서 보존되는지, 숨긴 도구를 직접 요청해도 거부하는지, 질문 대기 중 추가 호출이 없는지 확인한다. 재개 후 누적 한도와 동일 호출 ID의 완료 결과가 유지되고, 실제 문서 쓰기는 기존 승인 경로만 사용하는지 검증한다.

이번 수정은 README의 설계 계약 정리이며 registry.ts나 실행 코드는 바꾸지 않는다. 문서의 링크·HTML 표시 검증은 제품 실행 테스트와 구분한다. 구현 뒤에는 pnpm typecheck && pnpm test && pnpm boundaries && pnpm build를 수행한다.
