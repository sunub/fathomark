# 구현 순서와 검증 기준

상태: **설계 · 부분 구현** ([구현 현황](README.md#구현-현황))  
기준일: 2026-10-11  
[문서 목차](README.md)

첫 구현은 도구 수를 늘리기 전에 실행 계약을 연결한다. 아래는 후속 작업 계획이며 이번 문서 작성에서 제품 코드를 변경하거나 테스트를 실행했다는 뜻이 아니다.

1. 요청·행동·관측·근거·대기·검증 상태와 이벤트 정의. 기존 일반 채팅과 커리어 종료 규칙 분리.
2. 기존 Vault 도구를 연결하고 제한된 탐색과 작성 가능성 검사 구현.
3. `ask_user`의 질문 ID, 대기·재개·취소·누적 한도 구현.
4. 연결 문맥 조회와 공고 붙여넣기 지원. 외부 읽기·검색은 자료 범위 계약 후 확장.
5. 근거표·개요·초안과 필수 검증 연결. 필요한 경우에만 작업 상태 저장 도구 추가.
6. 부분 수정·검증·미리보기와 기존 승인 후 적용 연결.

| 검증 사례 | 관측 가능한 통과 조건 |
|---|---|
| 충분한 근거 | 탐색 → 초안 → 검증 → 미리보기 순서가 이벤트에 기록됨 |
| 근거 부족·중요한 충돌 | 초안 호출 0회, 승인 가능한 미리보기 0개 |
| 도구 호출 없는 탐색 응답 | 전체 완료가 아니라 작성 가능성 검사로 이동 |
| 검색 실패 | 결과 없음과 구분된 오류 상태 반환 |
| 질문 대기·재개 | 대기 중 모델·도구 추가 호출 0회, 재개 시 기존 한도 유지 |
| 중복·늦은 답변·취소 | 해당 응답으로 근거와 단계가 변경되지 않음 |
| 외부 조사 | Vault에서만 나온 비공개 표현의 외부 전송 차단 |
| 출처 혼입 | 공개 회사 사실·문체 예시를 개인 경험으로 사용한 반례 탐지 |
| 수정·재검증 | 수정 초안 최대 1회, 통과하면 진행·실패하면 적용 차단 |
| 부분 수정 | 역할·수치·성과 보존 여부와 변경 범위 확인 |
| 승인 전·폐기 후 | Vault 쓰기 0회 |
| 대상 변경·중복 승인 | 대상 변경 시 재승인, 동일 승인 적용 최대 1회 |
| 앱 재시작 | 오래된 대기·승인 자동 실행 없음 |

같은 문항·자료로 경험 발견률, 누락 해결률, 주장·출처 일치율, 불필요한 질문 수, 호출 수와 활성 시간을 비교한다. 개선 여부는 실제 평가 결과로 판단한다. 의미 검증의 오류 가능성은 남으며 “검증 통과”를 사실 오류가 전혀 없다는 보증으로 표현하지 않는다.

구현 후 필수 검사는 `pnpm typecheck && pnpm test && pnpm boundaries && pnpm build`다. 실제 Obsidian에서는 질문 대기·취소·문서 변경·승인·폐기·되돌리기를 확인한다.

이 문서와 이미지는 설계 검토용이다. 그림은 가독성을 위해 세부 입력 검사와 일부 상태를 생략했으므로, 연결선 표현이 모호하면 본문의 권한·종료·승인 계약을 기준으로 해석한다. 정확한 상태 형식과 도구 오류 계약은 구현 전에 확정한다.
