# Fathomark 서비스 방향 보고서

작성일: 2026-10-05. 근거: [ADR 0007](../adr/0007-grounded-career-writing-with-hosted-models.md), [subscription-cli-providers.md](subscription-cli-providers.md), [cli-agent-wrapping-token-economy.md](cli-agent-wrapping-token-economy.md), 2026-10-05 `codex exec` 실측. 코드는 수정하지 않았다. 이 문서는 제안이며 결정이 아니다.

## 1. 결론

Fathomark는 **"내 경험 기록에서 근거를 찾아 인용하며 지원서를 쓰게 하는 Obsidian 안의 작업대"** 로 만든다. 모델을 학습시키거나 모델 접근 방법을 만드는 것이 아니라, **근거를 찾고, 인용하고, 없는 경험은 쓰지 않는 과정**이 제품이다.

- 차별점은 문장 생성이 아니라 **출처 추적 가능성**이다. 모든 경험 주장은 Vault 노트로 되돌아가거나 "근거 없음"으로 표시된다.
- 모델은 교체 가능한 부품이다. 학습은 하지 않는다. 구독 CLI 연동은 선택적 접근 경로로 두고 제품의 중심에 두지 않는다.
- 첫 목표는 기능 확장이 아니라 **실제 지원 질문 몇 개로 검색과 인용이 맞는지 확인**하는 것이다(ADR 0007의 검증 단계).

## 2. 지금까지 확인된 사실

💡 **LoRA**: 모델 전체를 다시 학습하지 않고 작은 추가 가중치만 학습해 특정 용도나 문체에 맞추는 경량 미세조정 기법이다.

## 3. 실패에서 얻은 설계 원칙

1. **사실은 모델의 기억이 아니라 프롬프트에 넣는다.** 학습된 모델이 사실을 무시한 실험의 반대 접근이다. 사실은 매번 검색해 근거로 주입한다.
2. **문체는 사용자가 고른 예시로 준다.** 폴더 전체를 스캔해 추론하지 않는다(ADR 0006). 장르가 다른 글이 섞이면 결과가 오염된다는 것이 학습 실험의 교훈이다.
3. **작은 모델이 하는 정밀 추출을 믿지 않는다.** 숫자와 인용은 모델이 만들지 않고 노트에서 복사한다. 초안 단계에서는 인용 구간을 그대로 유지했는지 기계적으로 검사한다.
4. **검증 가능한 단계로 쪼갠다.** 자율 루프보다 고정 단계가 인용과 점검에 유리하다(ADR 0007). 각 단계는 구조화 출력으로 받아 파싱 실패를 "근거 없음"으로 처리한다.

## 4. 서비스 개념

**사용자가 하는 일**: 채용 공고나 지원 질문을 붙여 넣는다.

**시스템이 하는 일** (고정 순서)

1. 질문에서 요구 역량을 뽑는다.
2. Vault에서 후보 경험 노트를 찾는다. 경험 노트를 의견·스터디 노트보다 우선한다.
3. 근거로 쓸 노트와 원문 구간을 고르고 보여 준다. 사용자가 근거를 직접 추가·제외할 수 있다.
4. 선택한 근거와 사용자가 고른 문체 예시로 초안을 쓴다.
5. 주장마다 근거 구간을 연결해 검증한다. 연결이 없으면 "근거 없음"으로 표시한다.
6. 미리보기를 보여 주고 승인한 뒤에만 노트에 반영한다.

**기억해야 할 제품 규칙**: 근거가 없으면 지어내지 않고 "Vault에 이 경험이 없다"고 알린다. 이것이 사용자가 신뢰할 이유이다.

## 5. 모델 접근 전략

모델은 `provider` 어댑터 뒤에 둔다. 우선순위는 아래와 같다.

| 경로 | 역할 | 비고 |
|---|---|---|
| 호스티드 API(사용자 키) | 기본 | 약관이 가장 명확하다. 사용자가 종량 과금을 꺼릴 수 있다. |
| 로컬(Ollama) | 선택 | 이미 구현돼 있다. 품질 한계는 문서화한다. |
| 구독 CLI(Codex 우선) | 실험적 선택 | 사용자 기기의 수정되지 않은 공식 CLI만 호출한다. 토큰을 읽거나 저장하지 않는다. 호출당 고정 오버헤드와 한도 소모가 미확인이다. Claude는 약관 문의 전까지 제외한다. |

- 현재 `ModelProvider`는 네이티브 tool calling을 전제로 한다. 위 고정 단계는 도구 없는 "텍스트 입력, 구조화 출력" 호출로 충분하므로, 별도 인터페이스로 분리할지 설계 결정이 필요하다.
- 구독 경로를 쓰면 호출 수만큼 고정 오버헤드가 곱해지므로 단계를 묶는 설계가 필요하다.
- 어느 경로든 Vault 내용이 외부로 나가므로 요청마다 전송 내용을 보여 주는 동의 단계가 선행되어야 한다.

## 6. 하지 않을 것

- 사용자별 모델 학습(LoRA 포함)
- 코딩 에이전트식 자율 다단계 루프, 터미널 실행, 무제한 파일 접근(PRODUCT.md의 MVP 범위 밖)
- 구독 OAuth 토큰을 직접 읽어 쓰는 방식(계정 정지 위험)
- Vault 전체를 스캔해 문체를 추정하는 방식
- 여러 provider를 늘리는 것을 목표로 삼는 일

## 7. 검증 계획

기능을 더 만들기 전에 아래를 수동으로 통과시킨다.

1. 실제 지원 질문 5~10개로 검색을 돌려 정답 노트가 상위에 오는지 확인한다.
2. 초안의 각 주장이 노트에 연결되는지, 노트에 없는 주장이 "근거 없음"으로 잡히는지 확인한다.
3. 사용자가 문체를 받아들일 수 있는지 판단한다. 문체는 사실 검증을 통과한 뒤에만 평가한다(ADR 0006).

표본이 작으므로 결과는 방향 확인으로만 쓰고, 통과 기준은 사용자가 정한다.

## 8. 제안 순서

1. 검증 계획의 수동 실행으로 검색과 인용의 현재 상태 확인
2. 검색 개선(경험 노트 우선, 근거 없음 보고)과 주장 단위 검증
3. 도구 없는 호출 인터페이스 결정 후 provider 확장
4. 전송 동의 UX와 키 저장
5. 구독 CLI provider 실험(고정 오버헤드와 한도 소모 실측 후)

## 9. 아직 모르는 것

- 한국어 지원서 질문에서 현재 lexical 검색이 어느 정도 맞는가
- 문체 예시만으로 사용자가 만족할 문체가 나오는가(큰 모델로도 미검증)
- 구독 한도가 입력·캐시 토큰을 어떻게 세는가, 고정 오버헤드를 공식 방법으로 얼마나 줄일 수 있는가
- OpenAI 이용약관과 Anthropic 약관에서 앱이 사용자의 로컬 CLI를 호출하는 경우의 해석
- 이력서 bullet과 에세이 답변이 한 흐름으로 가능한가
- `model/` 워크스페이스의 보관 방식
