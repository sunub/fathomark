# S2 검색 품질 개선 보고서 (2026-10-06 ~ 10-08)

S2(검색 순위와 "근거 없음" 보고)가 합격선을 넘기까지 무엇을 문제로 봤고, 무엇을 고쳤고, 어떤 결과를 얻었는지 정리한다. 단계별 수치와 측정 조건은 [측정 문서](./career-retrieval-baseline.md)에 있다.

## 요약

- **결과: 합격.** 사용자가 새로 만든 판정용 셋 60개에서 네 지표를 모두 통과했다(recall@3 0.85, 차단률 0.95, 오차단률 0.00, 비경험 1위 0.03).
- **핵심 개선 두 가지.** 지원서 문항 머리말 청크를 의미 검색에서 뺐고, 후보 노트마다 Gemma가 "본인이 직접 한 일인가"를 판정하게 했다.
- **평가 방식도 고쳤다.** 판정용 셋과 같은 실패가 드러나는 개발용 셋을 새로 만들었고, 측정 조건과 처리 규칙을 측정 전에 고정했다.
- **남은 문제는 속도다.** 판정 때문에 검색이 질문당 0.1초에서 약 3.4초로 느려졌다.

## 무엇을 재는가

자기소개서를 쓸 때 근거가 되는 노트를 찾는 검색이다. 네 지표를 모두 만족해야 합격이다.

| 지표 | 뜻 | 합격선 |
|---|---|---|
| recall@3 | 답이 있는 질문에서 정답 노트가 상위 3개 안에 든 비율 | 0.75 이상 |
| 근거 없음 차단률 | 근거가 없어야 하는 질문에 "근거 없음"이라고 답한 비율 | 0.90 이상 |
| 오차단률 | 답이 있는 질문을 "근거 없음"으로 막은 비율 | 0.20 이하 |
| 비경험 1위 | 1등 노트가 경험 노트가 아닌 비율(공부·면접 준비 노트가 1등) | 0.10 이하 |

## 출발점

하이브리드 검색(어휘 검색 + `bge-m3` 임베딩, RRF로 합침)까지 구현한 상태에서 판정용 셋 27개를 쟀다.

| recall@3 | 차단률 | 오차단률 | 비경험 1위 |
|---|---|---|---|
| 0.70 | 0.86 (6/7) | 0.00 | 0.35 |

네 지표 중 하나만 통과했다. 이후 작업이 같은 단계를 반복하며 결론을 내지 못했다.

## 문제로 판단한 것

### 1. 끝내는 규칙이 없었다

- 합격선을 못 넘었을 때 어떻게 끝낼지 정해 둔 규칙이 없었다. 매번 선택지를 사용자에게 넘기고, 질문이 오면 새 갈래가 생겼다.
- 판정용 셋은 이미 두 번 써서 더 쓰면 오염된다. 개발용을 늘려도 합격 판정을 낼 수단이 없었다.
- 근거 없음 질문이 7개뿐이라 차단률 0.90은 7개를 모두 막아야 넘는다. 실제 능력이 정확히 0.90이어도 7/7이 나올 확률은 약 48%다.

### 2. 개발용 셋이 판정용보다 쉬웠다

- 같은 코드로 개발용은 recall 0.86, 비경험 1위 0.07이었고, 판정용은 0.70, 0.35였다. 개발용에서 나아져도 판정용에서 나아진다고 말할 수 없었다.
- 원인을 찾아보니 정답이 설정한 경험 폴더(`경험정리`, `sunub/이력서`, `resume`)에 몰려 있었다. 폴더 밖 경험 노트(`면접/`, `AI/` 등 15개)가 정답인 질문이 없었다.
- 폴더 기준 판별은 너무 좁으면서 동시에 너무 넓었다. 폴더 밖 경험 노트는 놓쳤고, 폴더 안의 면접 질문 목록이나 채용 공고는 경험으로 취급했다.

### 3. 지원서 문항 문장이 답변을 밀어냈다

- 자기소개서 노트는 회사 문항("~경험을 작성해주세요. 최대 500자")을 답변 옆에 둔다.
- 질문이 지원서 문항 형태면, 실제 답변보다 회사가 낸 문항 문장과 더 비슷하게 나와 상위를 차지했다.

### 4. 유사도로는 "내 경험"과 "언급"을 가를 수 없었다

- 끝까지 새는 근거 없음 질문은 단어가 실제로 노트에 있는 경우였다. 미래 계획("Unity를 활용해 경험을 축적할 것"), 팀원이 한 일(Redis), 채용 공고(Flutter), 학습 목표(파인튜닝)가 그 예다.
- 유사도 임계값을 올려 차단률 0.91을 맞추면 오차단률이 0.29가 됐다. 두 지표를 같이 맞추는 값이 없었다.

### 5. 평가 데이터에도 결함이 있었다

- 실제 문항 r11은 같은 지원서의 답변 노트가 제외 목록에서 빠져 있어서, "근거 없음"이 정답이 될 수 없었다.
- 노트 종류 라벨이 흔들렸다. 자기소개서인 `sunub/네이버랩스.md`가 `study`로, 면접 준비 가이드가 `experience`로 붙어 있었다.

## 개선한 것

| 문제 | 개선 | 효과(개발용 71개) |
|---|---|---|
| 개발용이 쉬움 | 폴더 밖 경험 노트가 정답인 질문과 "언급만 있는" 근거 없음 질문으로 새 개발용 셋 20개 작성 | 판정용과 같은 실패가 개발용에서 드러남(recall 0.58, 오차단률 0.42) |
| 문항 문장이 답변을 밀어냄 | 줄의 절반 넘게가 문항 문구인 청크를 의미 검색에서 제외 | 실제 문항 셋 오차단률 0.33 → 0.11 |
| 언급과 경험 구분 불가 | 후보 노트(융합 상위 6 + 의미 검색 상위 3)마다 Gemma에 "본인이 직접 한 일로 답하는가"를 묻고, "예"인 노트를 앞으로 올림 | 차단률 0.73 → 0.95, 비경험 1위 0.06 → 0.00 |
| 정답 후보가 밀려남 | 어휘 순위 때문에 밀린 의미 검색 상위 3개를 판정 후보에 추가 | 새 개발용 recall 0.67 → 0.75 |
| r11 라벨 오류 | 같은 지원서 답변 노트를 제외 목록에 추가 | 실제 문항 셋 차단률 계산이 바로잡힘 |
| 라벨 흔들림 | 질문을 보지 않고 미리 정한 기준으로 393개 노트를 다시 라벨링(67개 변경) | 비경험 1위가 라벨 실수에 덜 좌우됨 |
| 끝내는 규칙 없음 | 측정 조건(코드 해시, 모델 digest, 폴더 설정)과 합격·미달 시 처리를 측정 전에 문서로 고정. 측정 스크립트는 코드가 바뀌었거나 이미 쟀으면 실행을 거부 | 한 번의 측정으로 결론 |

판정을 켜지 않으면 검색은 기존과 똑같이 동작한다. Gemma가 없거나 실패하면 기존 유사도 임계값(0.58)으로 내려간다.

### 개발용 결과 (판정 없음 → 판정 있음)

| 셋 | recall@3 | 차단률 | 오차단률 | 비경험 1위 |
|---|---|---|---|---|
| 합계 71개 (49/22) | 0.78 → 0.84 | 0.73 → 0.95 | 0.16 → 0.04 | 0.06 → 0.00 |

## 시도했지만 버린 것

| 시도 | 결과 | 버린 이유 |
|---|---|---|
| 유사도 임계값만 조정 | 차단률 0.91에서 오차단률 0.29 | 두 지표를 같이 맞출 수 없음 |
| 문체(과거형 서술 비율)로 경험 노트 판별 | 자기소개서 초안과 면접 답변이 섞여 깔끔히 갈리지 않음 | 정확도 부족 |
| 융합 가중치와 RRF 상수 조정 | 새 개발용 recall이 0.67을 넘지 못함 | 한 문항 차이 흔들림, 과적합 위험 |
| 후보 15개를 한 번에 보여 주고 고르기 | 차단률 0.55 | Gemma가 거의 항상 무언가를 고름 |
| 근거 문장 인용 강제 | 차단률 0.50 | 아무 문장이나 인용함 |
| 판정 모델 `exaone3.5:7.8b`, `qwen3.5:9b` | 차단률 0.86, 0.77 | Gemma보다 관대함 |
| 핵심 행동을 먼저 적게 하는 프롬프트 | 지표 동일, 판정 시간 3.5초 → 5.2초 | 효과 없이 느려짐 |
| 외부 판정 모델(Jev) | 조사만 함 | 클라우드 API 전용이라 노트가 외부로 나감, 한국어 지원 미확인 |

## 최종 결과

사용자가 질문과 정답을 직접 만든 새 판정용 셋 60개(답 있음 40, 근거 없음 20)로 한 번 측정했다. 개선 작업을 한 쪽은 질문과 정답을 보지 않았다.

| 지표 | 합격선 | 결과 | 95% 신뢰구간 |
|---|---|---|---|
| recall@3 | 0.75 이상 | **0.85** (34/40) | 0.71 ~ 0.93 |
| 근거 없음 차단률 | 0.90 이상 | **0.95** (19/20) | 0.76 ~ 0.99 |
| 오차단률 | 0.20 이하 | **0.00** (0/40) | 0.00 ~ 0.09 |
| 비경험 1위 | 0.10 이하 | **0.03** (1/40) | 0.00 ~ 0.13 |

**합격.** MRR 0.72, 첫 색인 71초, 질문당 검색 3.4초.

## 남은 문제

- **속도.** 지연의 약 96%가 Gemma 판정이다. 질문당 평균 6.55회 호출, 한 번에 약 0.32초다. 판정을 빼면 0.1초다. "첫 '예'에서 멈추기"는 호출을 2.79회로 줄이지만 상위 3개 순위가 49개 질문 중 25개에서 바뀌어 보류했다. "색인할 때 청크마다 미리 판정"은 실험 중에 멈췄다.
- **차단률 여유가 한 문항이다.** 신뢰구간 아래쪽(0.76)은 합격선 밖이다.
- **라벨은 개선 작업을 한 쪽이 붙였다.** 질문은 보지 않았지만 완전히 중립적이지는 않다.
- **결과는 `gemma4:e4b`와 현재 프롬프트에 묶인다.** 모델, 프롬프트, 판정 방식(속도 개선 포함)이 바뀌면 새 판정용 셋으로 다시 재야 한다.
- **앱에는 아직 연결되지 않았다.** 판정은 평가 하네스에서만 켜진다. 연결하려면 `search_vault` 제한 시간(10초)을 늘려야 한다.
- **개발용 질문과 정답 일부는 개선 작업을 한 쪽이 만들었다.** 정답 노트를 읽은 상태에서 질문을 써서 실제보다 쉬울 수 있다.

## 다음 단계
