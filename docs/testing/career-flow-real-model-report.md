# 커리어 작성 흐름 실제 모델 연결 보고서 (2026-10-11)

[준비도 재평가](../../reports/2026-10-11-workflow-readiness-audit.md)는 "실제 모델의 글쓰기·의미 검증과 실제 Obsidian 동작을 평가하지 못했고, 의미 검사 테스트는 모의 모델의 판단을 미리 지정한 것"이라고 지적했다. 이 문서는 그 공백을 메우려고 한 작업에서 무엇이 문제였고, 어떻게 발견했고, 어떻게 고쳤는지 정리한다. 커밋은 `e64a632`부터 `46bd068`까지 24개다.

## 요약

- 로컬 `gemma4:e4b`로 커리어 흐름 전체를 Obsidian 없이 실행하는 평가 두 가지를 만들었다. 하나는 의미 검증기만 재고, 다른 하나는 요청부터 검증된 초안까지 전체를 잰다.
- 평가가 드러낸 문제를 고쳐 합성 Vault 기준 **검증된 초안 완료율이 0.25에서 0.81**로, **정답 근거 발견률이 0.63에서 1.00**으로 올랐다. 실행 오류는 22회 중 4회에서 0회가 됐다.
- 측정 중 **경험을 지어낸 초안이 검증을 통과하는 안전 문제**를 발견했다. 고친 뒤 근거 없는 문항 24회에서 지어낸 초안은 0건이었다.
- 실제 Obsidian 수동 확인은 하지 못했다. [체크리스트](./obsidian-manual-checklist.md)와 테스트 Vault 준비 스크립트만 만들었다.

수치는 합성 fixture Vault(경험 노트 6개 등 15개)와 작은 문항 세트로 잰 방향 확인용이다. 실제 Vault 합격 판정을 받은 것은 [S2 보고서](./career-retrieval-s2-report.md)의 검색 지표뿐이다.

## 평가 장치

| 평가 | 내용 | 실행 |
|---|---|---|
| 의미 검증 | 라벨된 초안 33개(역할 과장, 행동·수치 변경, 날조 성과, 문체·회사 사실 혼입, 문항 주제 끼워 넣기, 정상 초안)를 dev·heldout으로 나눠 검출률과 오차단율 측정 | `plugin/`에서 `FATHOMARK_LIVE_MODEL=gemma4:e4b npx vitest run tests/meaning-eval.test.ts` |
| 전체 흐름 | 기존 검색 문항 22개(답 있음 16, 근거 없음 6)로 워크플로 전체를 실행해 근거 발견·완료·인용·거부율, 질문 수, 호출 수, 시간 측정 | 같은 방식으로 `tests/career-eval.test.ts`. `FATHOMARK_LIVE_SEMANTIC=1`, `FATHOMARK_LIVE_JUDGE=1`이 앱 구성 |

두 평가 모두 환경 변수가 없으면 건너뛰고, 합격선을 두지 않고 수치만 출력한다. 워크플로는 의존성을 주입받는 함수라서 실제 Ollama 제공자, fixture Vault, "노트 밖 사실은 모른다"고 답하는 가상 사용자를 끼워 실행할 수 있다.

💡 **dev·heldout**: 프롬프트를 고칠 때 보는 사례(dev)와 고친 뒤 판정에만 쓰는 사례(heldout)를 나눈 것이다. 같은 사례에 맞춰 고치면 처음 보는 사례에서 성능이 떨어지는 과적합을 피하려는 장치다.

## 문제, 발견 방법, 수정

### 1. 연결할 수 없다던 Ollama는 실행 중이었다

- **문제.** 재평가는 `127.0.0.1:11434`에 연결할 수 없어 실제 모델 평가를 못 했다고 기록했다.
- **발견.** 샌드박스 밖에서 `ollama serve`를 시도하자 "address already in use"가 나왔다. 서버는 이미 떠 있었고 샌드박스 네트워크 제한이 연결을 막고 있었다.
- **수정.** 코드 변경 없음. 이후 측정은 샌드박스 밖에서 실행했다.

### 2. 숨은 사고 토큰이 출력 한도를 소모했다

- **문제.** 짧은 JSON 하나에 출력 토큰이 674개, 1,000자 초안에는 1,393개가 쓰여 한도 1,400에 닿았다.
- **발견.** `ollama show gemma4:e4b`에 `thinking` 기능이 있었고, 응답의 `message.thinking`에 provider가 읽지 않는 텍스트가 들어 있었다. 사고를 켠 경우와 끈 경우를 같은 사례로 비교했다. 끈 쪽이 출력 토큰 최대 233, 형식 수리 0회였고 의미 판정도 같거나 나았다.
- **수정.** 구조화 호출에 Ollama `format`으로 JSON 스키마를 강제하고 `think: false`를 보냈다(`e64a632`). 탐색 요청에도 같은 문제가 있어 실행이 "탐색 모델이 정상 완료하지 못했습니다"로 끝나는 것을 전체 흐름 평가에서 보고 따로 고쳤다(`8bedeae`). 평가 재현용 온도·시드 전달 경로도 추가했다(`7f17868`).

### 3. 의미 검증기는 거의 모든 초안을 통과시켰다

- **문제.** 모의 테스트에서는 역할 과장을 막았지만 실제 모델은 잘못된 초안의 0.29만 잡았다.
- **발견.** 의미 검증을 모듈로 분리하고(`415f8a0`) 라벨된 사례로 쟀다. 놓친 사례의 원 응답은 모두 `{"supported":true,"issues":[]}`였다. 스키마 첫 필드가 판정이라 모델이 비교 전에 결론부터 썼다.
- **수정.** 판정 앞에 주장별 대조 항목(주장, 근거 인용, 차이점, 의미 일치)을 두고, 항목 하나라도 어긋나면 모델 판정과 무관하게 코드가 막게 했다(`9ebe3d4`). 검출률은 0.29에서 0.94로 올랐고, 정상 초안 오차단은 0.00에서 0.20으로 늘었다. 사고를 켜는 방식은 더 나빠서 버렸다.

### 4. 응답 스키마를 토큰 추정에서 두 번 셌다

- **문제.** 출처가 두 개인 사례가 모두 "토큰 예산 초과"로 실패했다.
- **발견.** 요청 구성 요소별 추정치를 출력해 보니 스키마가 시스템 메시지와 `format` 필드 양쪽에서 계산됐다. Ollama에서 `format` 유무에 따른 `prompt_eval_count`가 같음을 확인했다.
- **수정.** 추정에서 응답 스키마를 뺐다(`05a1692`).

### 5. 바이트 수를 토큰 수로 써서 예산이 약 7배 과대 추정됐다

- **문제.** 요청 추정치 2,907에 실제 프롬프트 토큰은 392였다. 한국어 근거가 조금만 많아도 예산 초과로 막힐 상황이었다.
- **발견.** 모델 3종에서 내용 종류별 실제 토큰/바이트를 쟀다. 실제 글은 0.24~0.35, 숫자 나열은 1.0이었다. 기존 검증 프로필 설계(정수 배수)는 바이트 수 아래로 내려갈 수 없어 쓸 수 없었다.
- **수정.** 추정 비율을 0.5로 바꾸고, 요청 뷰 ÷ 비율이 모델 컨텍스트를 넘지 않는 관계를 테스트로 고정해 최악의 경우에도 잘림이 없게 했다. 커리어 도구 결과 한도도 같은 추정치로 계산했다(`b48e57f`). 측정값은 [tokenizer-profiles.md](./tokenizer-profiles.md)에 있다.

### 6. 정상 호출마다 처리되지 않은 AbortError가 남았다

- **문제.** Node에서 측정 스크립트가 성공한 호출 직후 죽었다.
- **발견.** 제품 provider만으로 재현한 뒤 `reader.cancel()`에 `catch`를 붙여 보니 그 promise가 원인이었다.
- **수정.** 별도 세션에서 고친 커밋을 가져왔다(`fc64840`, `d130012`).

### 7. 정답 노트를 찾고도, 또는 사소한 이유로 실행이 끝났다

전체 흐름 평가 기준선은 완료 0.25, 실행 오류 4건이었다. 실패 이유를 종류별로 나눠 결정적 버그부터 고쳤다.

| 문제 | 발견 | 수정 |
|---|---|---|
| `ask_user` 결과 한도 300이 스키마가 허용하는 한국어 최대 입력(약 1,420)보다 작아 정상 질문이 실패 | 실패 메시지 "result exceeds its 300 token estimate budget" 3건 | 한도를 최대 출력에 맞춤(`9dac4f9`) |
| 숫자 대조가 근거의 `2024-03`과 초안의 `2024년 3월`, `4명`과 `4인`을 다르게 판정 | 미완료 사유 "literal_mismatch 2024년" 3건 | 날짜 속 연·월과 인원 단위를 같은 값으로 인정, 기간으로 바꾼 표기는 계속 차단(`e26bb65`) |
| 모델이 잘못된 도구 입력을 보내면 실행 전체 종료 | "Invalid ask_user input" 1건 | 일반 채팅처럼 입력 오류는 1회 되돌려 수정 기회, 권한 거부는 건너뜀(`f817103`) |
| 모델이 추측한 경로의 노트가 없으면 실행 종료 | 이후 평가의 "not_found" 실패 | 탐색 중에는 결과를 모델에 알리고 계속(`919807f`) |

고친 뒤 완료 0.44, 실행 오류 0이 됐다.

### 8. 검증된 하이브리드 검색이 앱에 연결돼 있지 않았다

- **문제.** 남은 미완료 대부분은 검색이 정답 노트를 못 찾은 경우였다. "성능 문제 해결" 질의가 "p95 지연·캐시" 노트와 단어가 겹치지 않았다.
- **발견.** 결과 한도가 결과를 잘랐다는 가설을 먼저 확인했으나 틀렸다(검색 자체가 못 찾음). [S2 보고서](./career-retrieval-s2-report.md)를 보니 키워드 + `bge-m3` 임베딩 + Gemma 판정 구성이 실제 Vault 판정용 세트에서 합격했지만 앱에는 연결되지 않았다. 전체 흐름 평가에서 하이브리드는 근거 발견 1.00, 완료 0.88이었다.
- **수정.** 의미 검색과 판정을 설정(기본 켬)으로 연결했다. 시작 후와 커리어 실행마다 바뀐 노트만 백그라운드로 색인하고 플러그인 폴더에 저장하며, 임베딩 모델이 없으면 키워드로 돌아가고 설정 화면에 원인을 보인다. 판정 시간을 고려해 검색 제한을 30초로 늘렸다(`3c483ba`). 실행마다 갱신하면 수 MB 색인을 매번 쓰게 되는 문제도 미리 막았다(`eb08009`).

### 9. 경험을 지어낸 초안이 검증을 통과했다

- **문제.** 머신러닝 경험이 없는 Vault에서 "검색 품질 개선 프로젝트를 통해 머신러닝 모델을 서비스에 배포했다"는 초안이 완료됐다.
- **발견.** 근거 없는 문항이 2회 반복에서 모두 완료된 것을 보고, 사례 필터와 초안·인용 출력을 평가에 추가해(`2be0abd`) 재현했다. 작성 가능성 검사도 판정 필드가 맨 앞이라 주제만 비슷한 노트를 근거로 인정했고, 초안이 문항 주제를 끼워 넣었고, 긴 초안에서는 의미 검증이 섞인 날조를 놓쳤다. 실제 누출과 같은 형태의 긴 초안 사례를 추가하자 dev에서 5회 중 2회를 놓쳤다.
- **수정.** 세 단계를 함께 고쳤다.
  - 작성 가능성 검사는 필요한 사실마다 개인 출처 문장을 인용하게 하고, 인용이 그 출처에 실제로 있는지 코드로 확인한다(`0de9a69`).
  - 의미 검증은 주장을 원자 사실로 나눈 뒤 근거와 대조한다(`0de9a69`). dev 검출 1.00·오차단 0.17, heldout 검출 0.93·오차단 0.28.
  - 검증이 엄격해지자 초안이 근거에 없는 역할·평가로 분량을 채우는 습관 때문에 완료율이 0.56으로 떨어졌다. 초안·수리 단계에 그런 표현을 덧붙이지 말고 근거가 짧으면 짧게 쓰라고 지시했다(`4443aed`). 완료는 dev 0.72, heldout 0.93으로 회복했다.

💡 **원자 사실 분해**: 긴 문장을 사실 하나씩으로 나눠 따로 검증하는 방식이다. 여러 사실이 섞인 문장에서 틀린 하나가 묻히지 않게 한다.

### 10. 사용 흐름의 빈틈

- **미리보기 재생성.** 문서가 바뀐 뒤 다시 만들기를 누르면 커리어 모드에서는 미리보기가 안내 없이 사라졌다. 재평가 지적을 코드로 따라가다가 차단 사유 조회도 `null`을 돌려준다는 것을 확인했다. 재실행·재검증 안내를 표시하게 했다(`2f3e1aa`).
- **후속 요청.** 요청마다 근거와 대화가 비어 시작해 "더 짧게"가 이전 초안을 참조하지 못했다. 이전 근거와 적용 전 초안을 넘기고, 선택 문단이 없으면 이전 초안을 탐색 없이 수정한다(`5988b18`). 구현 중 이어받은 근거가 요청마다 계속 쌓인다는 것을 발견해, 완료된 실행은 초안이 인용한 근거만 넘기게 했다. 이전 초안은 모델이 쓴 글이므로 근거로 등록하지 않는다.

### 11. 문서와 주석이 코드보다 뒤처져 있었다

설계 문서 22개가 "구현 전", 개요가 "빈 도구 목록과 가짜 모델"이라고 설명했고, 도구 등록 주석도 실제와 달랐다. 상태 표시와 사실 진술을 고치고 [설계 README](../design/workflow/README.md#구현-현황)에 구현 현황·측정값·알려진 위험을 모았다(`46bd068`, `297f41a`). HTML 사본은 생성 스크립트가 없어 초판으로 두고 Markdown을 기준으로 명시했다.

## 측정 방법에서 배운 것

- **같은 Ollama에 평가를 동시에 돌리면 수치가 무효가 된다.** 두 평가를 겹쳐 실행하자 판정 검색이 30초 제한을 넘어 대부분 실패로 기록됐다. 그 결과는 버리고 순차로 다시 쟀다.
- **작은 표본으로 결론을 내리지 않는다.** 처음 5개 사례로 잰 의미 검증은 15/15였지만 27개로 늘리자 0.29였다.
- **가설은 데이터로 확인한다.** 검색 결과 한도가 정답을 잘랐다는 가설은 측정으로 틀렸음을 확인했다. 프롬프트 축약(156바이트 절약)은 오차단을 0.20에서 0.42로 올려 되돌렸다.

## 남은 문제

- 근거가 많이 모이면 요청이 토큰 예산을 넘는다(최종 평가 68회 중 1회). 근거 선별·압축 단계가 없다.
- 모델이 바쁘면 판정 검색이 제한 시간을 넘고 실행이 실패한다.
