# 커리어 검색 기준선 (S1)

측정일: 2026-10-05. 대상: `plugin/src/tools/vault-search.ts`의 현재 lexical `searchVault`(질문 전체를 그대로 질의로 사용). 데이터: `plugin/tests/fixtures/career-vault/`의 합성 노트 15개(경험 6, 의견 3, 스터디 4, 기타 2)와 `career-cases.json`의 12개 질문(답이 있는 질문 9, 근거가 없어야 하는 질문 3). 재현: `pnpm vitest run tests/retrieval-baseline.test.ts`.

표본이 작고 합성 데이터라 숫자는 방향 확인용이다. 통계적 결론을 내리지 않는다.

## 결과

| 지표 | 값 |
|---|---|
| recall@3 (답이 있는 질문 9개) | 0.44 |
| MRR | 0.33 |
| abstention (근거가 없어야 하는 3개 중 "근거 없음"으로 응답한 비율) | 0.00 |

abstention 기준: 현재 검색에는 지원 여부 신호가 없어서 결과가 하나라도 있으면 "지원됨"으로 계산했다. 세 질문 모두 결과가 나와서 0이다.

## 관찰된 문제 (S2가 다룬다)

1. **의견·스터디 노트가 경험 노트보다 위에 온다.** "서비스 성능을 개선한 경험"은 의견 노트 `성능-최적화에-대한-생각`이 1위, 경험 노트가 2위다. ADR 0007이 지적한 문제가 합성 데이터에서도 재현된다.
2. **조사가 붙은 질문어가 일치하지 않는다.** "장애를 해결한 경험"은 결과가 비어 있다(질문의 `장애를`이 노트의 `장애`와 부분 문자열로 맞지 않는 경우). "팀을 이끈 리더십 경험"은 경험 노트가 빠지고 의견 노트만 나온다.
3. **일반 단어가 매칭을 만든다.** "경험", "서비스" 같은 질문 상투어가 거의 모든 노트와 맞아서 근거가 없는 질문(블록체인, iOS, 머신러닝)에도 같은 노트들이 나온다.
4. **의미가 가깝지만 단어가 다른 질문은 못 찾는다.** "수작업을 자동화한 경험"은 단어가 달라 정답을 놓친다. lexical 방식의 한계이며, 임베딩은 S2의 개선이 목표에 못 미칠 때만 검토한다(ROADMAP Phase 3).

## S2 결과 (2026-10-06)

구성 A는 위 기준선(원래 `searchVault`)이고, E는 S2의 최종 구성이다. 수치는 방향 확인용이다. 표본이 작고 합성 데이터다.

### 단계별 변화 (고정셋 12개, 답이 있는 질문 9개)

| 구성 | 변경 | recall@3 | MRR | abstention |
|---|---|---|---|---|
| A | 기준선 | 0.44 | 0.33 | 0.00 |
| B | IDF + MSM | 0.11 | 0.11 | 1.00 |
| C | B + 경험 노트 ×3, 제목·헤딩 가중 | 0.11 | 0.11 | 1.00 |
| D | C + 조사 처리 | 0.11 | 0.11 | 0.67 |
| (계획에 없던 추가) | D + 질문 틀 단어 제거 | 0.33 | 0.33 | 1.00 |
| E | + 하다 동사 어미 처리, `supported` 판정(0.5) | 0.33 | 0.33 | 1.00 |

- B가 recall을 크게 떨어뜨린 이유는 조사·어미가 붙은 질문 단어가 MSM 분모를 키웠기 때문이다. 조사 처리(D)만으로는 회복되지 않았고, 모든 질문에 붙는 틀 단어("경험", "설명해", "주세요" 등)를 빼자 0.33으로 올랐다.
- 하다 동사 어미 처리는 고정셋 수치를 바꾸지 않았다. 고유어 동사("이끈", "줄인")는 처리하지 않는다.
- 구성별 수치는 개발 중에 측정한 것이라 A와 E만 같은 스크립트로 재현했다. B~D는 당시 출력 기준이다.

### 보류 셋 (질문 10개, 구현 중 사용하지 않고 마지막에 한 번 측정)

| | recall@3 | MRR | abstention | 답이 있는데 "근거 없음"으로 막힌 질문 |
|---|---|---|---|---|
| A | 1.00 | 1.00 | 0.00 | 0/7 |
| E | 0.86 | 0.86 | 1.00 | 2/7 |

- 질문별: 개선 3(모두 근거 없는 질문), 악화 1(`h-multi`), 동일 6. 고정셋: 개선 5, 악화 3, 동일 4.
- 유형별 recall@3(근거 없는 질문은 "없음"으로 응답한 비율): 고정셋 semantic A 0.50 → E 0.00, keyword 0.40 → 0.60, no_answer 0.00 → 1.00. 보류 셋은 `multi_doc` 1.00 → 0.00 외에는 A와 E가 같다.
- **해석 주의:** 보류 질문은 합성 노트의 내용을 읽고 쓴 것이라 노트와 단어가 많이 겹친다. 그래서 원래 검색(A)이 7개를 모두 맞혔고, 의미는 같지만 단어가 다른 질문을 거의 담지 못했다. 이 셋은 `semantic` 약점을 재는 데는 부족하다.

### 완료 기준 점검

| 기준 | 결과 |
|---|---|
| 고정셋 recall@3이 기준선(0.44)보다 개선 | **미달** (0.33) |
| 의견 노트가 경험 노트보다 상위에 오지 않음 | **미달** (`perf`, `lead`에서 의견 노트가 1위이고 `supported=true`) |
| 근거 없는 질문은 `supported: false` | 달성 (고정셋 3/3, 보류 셋 3/3) |
| 보류 셋에서도 기준선보다 개선 | **미달** (recall@3 1.00 → 0.86). 근거 없음 판정만 개선 |

### 알려진 한계와 후속 과제

1. **`supported` 임계값 0.5는 검증되지 않았다.** 고정셋에서 정답 노트와 오답 노트의 커버리지가 같은 범위(0.41~1.00)에 섞여 있어 값을 정할 근거가 나오지 않았다. 근거 없는 질문은 MSM에서 먼저 걸러져 임계값에 닿지 않는다. 답이 있는 질문이 막히는 비율(고정셋 5/9, 보류 셋 2/7)이 높다.
2. **의견 노트가 근거로 인정된다.** 점수와 판정 모두 노트 종류를 보지 않고 질문 단어를 맞춘 정도만 본다. 판정을 "경험 노트가 있으면 그 노트의 커버리지만 본다"로 바꾸는 방안이 있으나 계획 범위를 넘어 보류했다.
3. **노트 분류는 사용자가 직접 줘야 한다.** 경험 노트 판별은 프론트매터 `type`, 태그, 폴더 규칙이다. 설정에 "경험 폴더"를 추가했고 비어 있으면 `type: experience`만 쓴다. 규칙이 없는 Vault에서는 종류 가중치가 적용되지 않는다. 노트 내용으로 경험 여부를 판단하는 방법(휴리스틱, 모델 판정)은 아직 없다.
4. **어휘 불일치(semantic).** 고정셋의 `latency`, `ci`, `lead`, `conflict`, `search`는 질문과 노트의 단어가 다르다("성능"/"지연", "리더십"/"리드", "갈등"/"충돌", "배포"/"빌드"). 단어 기반 검색으로는 풀리지 않는다.
5. **`searchVault`는 아직 어디에도 등록되어 있지 않다.** `main.ts`의 `ToolRegistry`가 비어 있어, 경험 폴더 설정은 `registerVaultTools`가 규칙을 받는 곳까지만 연결되어 있다. 실제 등록은 S4에서 한다.

### 의미 검색 도입 판단 (결정 게이트)

목표에 못 미쳤고 부족분의 상당수가 단어가 달라서 생기는 `semantic` 유형이다(고정셋 4개 중 recall@3 0). 계획의 순서(Ollama 임베딩 API → 플러그인 내 `transformers.js` → Python 추론 서버)대로 검토할 근거가 있다. 다만 어휘 불일치에는 질문 확장(동의어)이나 노트 쪽 별칭 같은 더 가벼운 방법도 있고, 의견 노트 문제는 임베딩으로 풀리지 않는다. 판단은 이 문서를 근거로 별도로 한다. 이 슬라이스에서는 구현하지 않는다.

## 실제 Vault 평가 (2026-10-06)

합성 데이터로는 합격 판정을 할 수 없어서 실제 Obsidian Vault(노트 393개)로 S2 합격선을 쟀다. 판정용으로 한 번 측정했고 이 수치로 튜닝하지 않는다.

| 지표 | 합격선 | 폴더 미설정 | `경험정리` 설정 |
|---|---|---|---|
| recall@3 (any-hit) | 0.75 이상 | 0.40 | 0.35 |
| 근거 없음 차단률 | 0.90 이상 | 0.57 | 0.57 |
| 오차단률 | 0.20 이하 | 0.05 | 0.05 |
| 비경험 노트 1위 | 0.10 이하 | 0.55 | 0.50 |

**판정: 미달.** 질문 27개(답 있음 20, 근거 없음 7). MRR 0.37.

**관찰**

- 근거 없음 7개 중 3개(쿠버네티스, 매출, A/B 테스트)를 막지 못했다. "운영", "서비스" 같은 일반 단어가 여러 노트에 걸려 커버리지가 0.5를 넘는다.
- 오차단률이 낮은 것은 거의 모든 질문에 `supported: true`를 내기 때문이기도 하다.
- 이 Vault의 경험은 `경험정리`, `resume`, `sunub/이력서`, `면접`에 흩어져 있다. 경험 폴더 설정이 하나뿐이라 효과가 작았다(1위 비경험 0.55 → 0.50).
- 같은 경험이 자기소개서, 이력서, 포트폴리오에 중복돼 있어 recall@3은 any-hit(정답 중 하나라도 상위 3개)으로 센다.

**한계**

- 정답 노트를 고를 때 질문 단어가 아닌 노트의 고유 단어(`KTX2`, `Zod` 등) 포함 횟수를 일부 썼다. 현재 검색(단어 매칭)에 유리하게 나올 수 있다.
- 답 있음 20개라 한 질문이 0.05를 움직인다.
- 노트 종류 라벨은 폴더 규칙과 파일 목록으로 정했다(경험: `경험정리/`, `sunub/이력서/`, 일부 `resume/`·`면접/` 파일).

### 다시 돌리는 방법

질문, 정답, 노트 종류 라벨은 개인 정보라 저장소에 없다. 로컬에 다음 세 파일을 둔다.

- `cases.json`: `[{ id, question, expected: [Vault 상대 경로], shouldAbstain }]`
- `kinds.json`: `{ "Vault 상대 경로": "experience" | "study" | "prep" | "other" }`
- Vault 경로

```bash
cd plugin && FATHOMARK_LOCAL_VAULT=<Vault 절대 경로> FATHOMARK_LOCAL_CASES=<cases.json> FATHOMARK_LOCAL_KINDS=<kinds.json> [FATHOMARK_LOCAL_FOLDER=경험정리] pnpm vitest run tests/local-vault-eval.test.ts
```

환경변수가 없으면 이 테스트는 건너뛴다(`pnpm test`에 영향 없음). 출력은 질문 id, 순위, 지표만 담고 노트 제목과 본문은 담지 않는다. 합격 계산은 `plugin/tests/support/pass-line.ts`가 한다.

## 근거 판정과 문항 머리말 제외 (2026-10-07, 개발용)

하이브리드 검색(임베딩 + 어휘, RRF)은 판정용에서 recall 0.70, 차단률 0.86(6/7), 오차단률 0.00, 비경험 1위 0.35로 미달이었다. 판정용은 이미 두 번 측정해서 더 쓰지 않았다. 이번 개선은 개발용 셋만 보고 했다.

**바꾼 것**

- **문항 머리말 청크 제외.** 자기소개서 노트는 회사 문항("~경험을 작성해주세요. 최대 500자")을 답변 옆에 둔다. 문항형 질문은 답변보다 이 머리말에 더 가깝게 나와서 답변을 밀어냈다. 줄의 절반 넘게가 문항 문구인 청크는 의미 검색에서 뺀다(`isAnswerChunk`).
- **Gemma 근거 판정.** 유사도 임계값은 "내가 한 일"과 "하고 싶은 일, 팀원이 한 일, 채용 공고 문구"를 가르지 못한다. 융합 상위 6개와 의미 검색 상위 3개 노트마다 가장 가까운 청크 2개를 `gemma4:e4b`에 보여 주고, 본인이 직접 한 경험으로 질문에 답하는지 묻는다. 하나라도 "예"면 근거 있음이고, "예"인 노트를 맨 앞으로 올린다. 영문 기술어 게이트와 유사도 하한(0.45)에 걸리면 판정을 부르지 않는다. 판정이 실패하면 기존 임계값(0.58)으로 내려간다.
- 판정을 켜지 않으면 동작은 기존과 같다(개발용 수치 동일).

**개발용 결과** (`경험정리, sunub/이력서, resume` 설정)

| 셋 | 질문 | recall@3 | 차단률 | 오차단률 | 비경험 1위 |
|---|---|---|---|---|---|
| 합격선 | | 0.75 이상 | 0.90 이상 | 0.20 이하 | 0.10 이하 |
| 기존 개발용 | 40 (28/12) | 0.86 → **0.89** | 0.83 → **1.00** | 0.07 → **0.00** | 0.07 → **0.00** |
| 실제 문항 | 11 (9/2) | 0.78 → 0.78 | 0.50 → **1.00** | 0.11 → **0.00** | 0.00 → 0.00 |
| 새 개발용 | 20 (12/8) | 0.58 → **0.75** | 0.63 → 0.88 (7/8) | 0.42 → **0.17** | 0.08 → **0.00** |
| 합계 | 71 (49/22) | 0.78 → **0.84** | 0.73 → **0.95** (21/22) | 0.16 → **0.04** | 0.06 → **0.00** |

화살표 왼쪽은 판정 없음, 오른쪽은 판정 있음이다. 합계는 네 지표 모두 합격선 안이다. 새 개발용 셋은 차단률이 한 문항(파인튜닝 질문에 성능 개선 문단을 "예"로 판정) 차이로 미달이다.

**새 개발용 셋.** 판정용과의 격차를 드러내려고 만들었다. 정답이 설정 폴더 밖(`면접/`, `AI/`)에 있는 질문 12개와, 언급은 있지만 본인 경험이 아닌 근거 없음 질문 8개(채용 공고 복사본, 학습 목표 문장, 스터디 노트)다. 이 셋에서 기존 설정은 recall 0.58, 오차단률 0.42였다.

**평가 데이터 수정.** 실제 문항 r11(카카오페이 UI/UX)은 같은 지원서의 답변 노트(`sunub/이력서/카카오페이/` 아래 문항 이름 파일)가 제외 목록에 빠져 있었다. leave-one-out 원칙대로 제외 목록에 추가했다.

**비용.** 질문당 판정 호출 6~9회, 검색 시간 평균 약 3초(최대 약 8초). `search_vault` 도구의 제한 시간은 10초라서, 앱에 연결할 때 늘려야 한다.

**검토하고 버린 것** (개발용 합계 기준)

- 유사도 임계값만 조정: 차단률 0.91에서 오차단률 0.29. 둘을 함께 맞추는 값이 없다.
- 문체(과거형 서술 비율)로 경험 노트 판별: 공부 노트로 라벨된 자기소개서 초안, 면접 준비 노트의 1인칭 답변 때문에 깔끔하게 갈리지 않는다.
- 융합 가중치와 RRF 상수 조정: 새 개발용 recall이 0.67을 넘지 않고, 한 문항 차이 흔들림이다.
- 후보 15개를 한 번에 보여 주고 고르게 하기: Gemma가 거의 항상 무언가를 골라 차단률이 0.55로 떨어졌다.
